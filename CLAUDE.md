# CLAUDE.md — Itinerary

Operational rules and invariants. Read this before making changes.

## What this is
Hyperlocal AI day-planner. Free-text prompt → one executable outing (real venues, real times, real transit), rendered on a map, that heals itself when transit breaks. The user supplies the CITY and starting address (Toronto/Ossington is the prefilled default and the pre-multi-city fallback, no longer the only target); each plan carries its own resolved IANA timezone. Next.js, OpenRouter (an ordered per-call-type model chain, `meta-llama/llama-3.3-70b-instruct` first — see the models section), Google Geocoding/Places/Routes/Weather/Maps, and Firebase Auth for OPTIONAL Google sign-in (the app is fully usable with no account).

## Core architecture rule (governs everything)
The LLM does semantic work only: shaping the day, selecting venues, writing reasons. Code does every verifiable fact: hours, prices, ratings, distances, travel times, scheduling. Never let the LLM compute distance/time or check "is it open" — that's a field comparison, not a judgment call. If a change asks the LLM to do something checkable, that's the bug.

The LLM is a PROPOSER, never an authority. Its plan is an input code validates, exactly as `selectVenues()` treats its own output (invalid ids → one retry → deterministic fallback; "a correction is not trusted merely because it parsed"). It proposes intent and estimates; code owns the arithmetic — real travel legs, real opening hours, actual end times, whether the plan genuinely fits the window. If the planner says four activities fit between 3 and 8 and the real legs make it six hours, code catches that: the LLM never gets to be wrong about a number that can be checked.

## Models and the fallback chain (`app/api/_shared/models.ts` + `modelFallback.ts`)
ONE file owns every model id. It replaced three independent `const MODEL` declarations (parse/select/swap) — the reason a model change used to mean editing three files and remembering all three existed. Chains are ORDERED and PER CALL TYPE, env-overridable via `OPENROUTER_MODELS_PLANNER` / `_SELECT` / `_SWAP` with in-code defaults.
- **Why per call type, not one chain.** The ORIGINAL reason was Groq's per-model rate limits, and that half is WEAKER under OpenRouter (account credit is shared across models) — do not re-derive this split from rate limits alone. What survives is task fit: `meta-llama/llama-3.1-8b-instruct` classifies swap intents correctly (with `parseTimeExpr`/`parseDurationExpr` owning the numbers underneath) but in SELECT it picked a venue with no evidence for a hard constraint — the exact hedge the prompt forbids. Never put the swap primary on the select chain.
- **Only 429 and provider-side 5xx advance the chain** (`ProviderError.isModelRetryable`). A 401/403 is the same key failing identically on every model, so advancing burns the chain and buries the real problem; a 400 is our own malformed request. `readProviderJson` no longer discards the status: `ProviderFailure` carries `upstreamStatus` + `retryAfterSeconds`, and 429 gets its own `*_rate_limited` code. The public message/status stay generic — this is about what the SERVER knows.
- **The fallback wraps ONE LOGICAL CALL**, which for the planner and select includes their own correction retry. A correction is a reply in a conversation; letting it land on a different model than the answer it corrects is a subtler bug than the rate limit it works around. `selectModelCall(apiKey, model)` exists to bind a completion to one model across that ladder.
- **Chain exhaustion is a 503 `model_capacity_exhausted`** with an actionable message and `Retry-After` — never the generic provider text. EXCEPT swap, where exhaustion falls to the deterministic `localFallback()`: that call has real parsers beneath it, so degrading beats refusing. That is a decision, documented at the call site.
- **THE TRANSPORT IS OPENROUTER (migrated 2026-08-15), and THREE request fields are load-bearing.** `app/api/_shared/openrouter.ts` is THE place the endpoint and the body are spelled; all three call sites (parse, select, swap) import `OPENROUTER_URL` + `chatCompletionBody`, exactly as they all import `modelChain`. The URL is HARDCODED on purpose — no base-URL env var — and the key is `OPENROUTER_API_KEY`. The body is otherwise byte-identical to the Groq era (`messages`, `response_format: {type:"json_object"}`, `temperature: 0`, and `choices[0].message.content` read back the same way), which is what made this a transport swap rather than a rewrite.
  - **`provider: { require_parameters: true }` IS THE JSON-MODE SAFETY NET.** JSON support is a property of the serving ENDPOINT, not the model. An endpoint that lacks it does not error — OpenRouter SILENTLY DROPS `response_format` and the model answers in PROSE, which every parser here reads as a malformed model. This flag pins routing to endpoints supporting every parameter sent, so "no compliant endpoint" becomes a 5xx, and a 5xx advances the chain. Never remove it, and never add a fourth call site without it.
  - **`provider.sort: "throughput"` IS THE SPEED FIX, and the default it replaces is a LOTTERY (added 2026-08-15).** OpenRouter's default routing is price-weighted and LOAD-BALANCES across the compliant endpoints, so the same request lands somewhere different each time. Measured live on the real planner prompt: the same call was served by DeepInfra at **5.7 tok/s**, AkashML at 43, and SambaNova at 147 — and the slow end is not a tail, it is a ~58s generation for a four-activity plan, past even the 45s server budget. That is the diagnosed bug (a plan taking ~21s and dying on the CLIENT deadline); routing overhead was never it, at 59ms. `sort: "throughput"` orders by generation speed instead, and composes with `require_parameters` in that order — **the flag filters to endpoints that genuinely support every parameter sent, and `sort` picks the fastest of what SURVIVES.** Fastest COMPLIANT endpoint, never fastest outright. Re-measured after: Groq, ~288-310 tok/s, ~1s end to end, on both prompts, both runs — the consistency is the point as much as the speed. **NEVER replace this with `order: ["<provider>"]`.** A provider pin names something that is not ours: providers serve different subsets of models, so a pin hard-couples the body to today's chain and breaks silently the day `models.ts` changes — the exact drift `models.ts` exists to end, one file over. `sort` + `max_price` name no provider and no model, so they survive a chain change (Phase 2) untouched; a test pins that the routing block contains no model id and no `order`/`only`/`ignore`.
  - **`provider.max_price` is the ceiling throughput-sorting removed, and the OBVIOUS NUMBER IS WRONG.** Sorting by throughput takes price out of the ordering entirely, so nothing would stop routing at a fast-but-premium endpoint; the cap is `{ prompt: 5, completion: 10 }` USD per MILLION tokens. **It is a FILTER — a cap set too low deletes a legitimate endpoint silently rather than erroring**, which is why the number was probed per ENDPOINT (`GET /api/v1/models/{id}/endpoints`) and not taken from the blended per-model figure: across the four chain models the priciest endpoint is $1.04/M prompt (Together on llama-3.3-70b) and **$2.253/M completion (Cloudflare, same model)**, so a round `completion: 2` would have quietly dropped it. 5/10 clears every chain endpoint by ~4.5x and still refuses frontier-model pricing. Raise it, never delete it. **The honest cost of the whole change: ~$0.002 per planner call against ~$0.0005 on the cheapest endpoint** — Groq is genuinely dearer than DeepInfra. Speed costs money, this is the trade, and the ceiling is what bounds it.
  - **`reasoning: { effort: "low", exclude: true }` is sent ONLY to reasoning-mandatory models (the `gpt-oss` entries), because require_parameters CUTS BOTH WAYS.** It keeps reasoning tokens out of `message.content` and shortens the preamble — but sending it to `meta-llama/llama-3.3-70b-instruct`, which is not a reasoning model, would filter routing on a parameter it does not have and leave the request with NO endpoint, killing the primary on both the planner and select chains. The gate is the MODEL, not the call site. LIVE-PROBE ITEM, unprovable offline: that reasoning genuinely lands in `message.reasoning` and never leaks into `content` — a leak breaks all three call sites at once.
  - **A 200 CAN BE A FAILURE, and `readProviderJson` now says so.** OpenRouter answers some rejections (a rate limit among them) with HTTP 200 and `{ error: { code, message } }` in the BODY. Checking `response.ok` alone let that through: `choices` came back undefined, the call site threw its own `*_invalid_response`, and that error carries no `upstreamStatus` — so `isModelRetryable` was false and THE CHAIN NEVER ADVANCED, burning the request the fallback exists to save. The guard is deliberately narrow on both sides: a body carrying `choices` is never an error, and `error` must be an OBJECT (Upstash answers with `{error: "<string>"}`, and Redis behaviour must not move). An unreadable code degrades to a retryable 502.
  - **The timeout is 45s** (`PROVIDER_TIMEOUT_MS.openrouter`), up from Groq's 20s: OpenRouter routes to whichever upstream serves the model, and two of three chain entries think before answering. It matters more than it looks — `fetchProvider` throws a timeout with NO `failure`, so `isModelRetryable` is false and a timeout does NOT advance the chain. **The BROWSER is still the binding ceiling and that is deliberate**, but it is no longer 15s: `DEFAULT_CLIENT_FETCH_TIMEOUT_MS` is **25s** (raised 2026-08-15, still no caller overriding it — one deadline for all 19 `fetchJson` call sites in `page.tsx`). The "FLAGGED, NOT FIXED" recorded here is RESOLVED, and by the throughput routing above rather than by the constant: the fast path is ~1s, so 25s is headroom for the tail — one LLM-backed request can legitimately cost several sequential model calls (a correction retry, then the next model in the chain) — not a fix in its own right. Not raised to meet 45s: past ~25s the honest answer to a user watching a spinner is that something is wrong, and every non-LLM route (geocode, store, weather) answers in well under a second or is broken. The cost is paid only on failure — a hung request now reports ten seconds later.
- **Never pick a chain model from memory.** Probe `GET https://openrouter.ai/api/v1/models` and run the candidate against the real system prompt in JSON mode. `qwen/qwen3.6-27b` failed JSON validation and `groq/compound-mini` is an agentic tool-using system — both were rejected that way. A chain entry that cannot hold the contract is worse than a shorter chain. Under OpenRouter there is a SECOND question, and it is about ENDPOINTS rather than the model: a model id resolves to one of several, so confirm at least one of them BOTH supports `response_format` AND sits under the `max_price` ceiling — `GET /api/v1/models/{id}/endpoints` reports both per endpoint, which the per-model figure blends away. Routing filters on each independently and neither failure announces itself. See the routing gotchas below.
- **A weaker fallback is safe because the validation ladders are untouched.** `findPlanProblems`/`findProblems` → correction retry → deterministic fallback catches junk from any model; `gpt-oss-120b` returning `activities: []` on a vague prompt was caught and rescued by exactly that machinery. Do not weaken any of it to accommodate a weaker model — that is what makes this change low-risk. Every attempt is logged (`model_call`, `model_unavailable`, `model_chain_exhausted`): running degraded silently is worse than running degraded.

## The pipeline (in order)
typed city/address geocode → LLM PLANNER → [clarifying questions, one round] → weather fetch → Places search (one per activity; bounded late-night expansion) → objective filter → LLM select (+ duration refinement) → travel (computeRoutes) → schedule + window validation → map. Each step is its own module and was built/tested in isolation.

**The geocode runs FIRST** (reordered 2026-07-27): the planner resolves "tonight"/"in an hour" against a real clock, so it has to be told WHICH clock, and only the geocode knows the plan's zone.

## The planner (`app/api/parse/planner.ts` + `app/api/parse/route.ts`)
`/api/parse` is a PLANNER, not an extractor. It is sent the prompt, the city, — the key enabler — the current instant in the plan's timezone with the weekday named, and (Stage 3B, only for a verified non-anonymous caller with a stored profile) a `preferences` object. It returns `{ activities, timeIntent, questions, context }`: which activities make the day, what to search for per activity, a duration estimate per activity, a resolved start/end, and up to three clarifying questions. `planToParsed()` projects that onto `ParsedPrompt`, so Places/filter/select/swap/reroute/the store all keep working unchanged.
- **`time_window` is PROSE now.** On the planner path it is a display label only; the resolved instant travels explicitly (`targetTime` into the search route, `startOverride` into `buildSchedule`) so search, the hours filter, the weather gate and the schedule all share ONE anchor. `resolveStartTime`'s category defaults survive as the fallback for callers that don't come through the planner (swap, reroute, legacy stored plans).
- **`stop_count` is always null** on the planner path: the activity list IS the count.
- **Validation is non-negotiable** and mirrors `selectVenues`: `findPlanProblems()` → one correction retry with the problems spelled out → a deterministic fallback (one general activity at the next full hour + the broad questions). A raw model error never reaches the user. Durations are CLAMPED (15–360) rather than rejected — arithmetic code can fix does not deserve the one retry, and the same bargain covers a window the user is already INSIDE: `windowUnderway()` clamps a past start up to `now` and keeps the stated end, because "5-9pm" asked at 6:30 is a real still-open window, not the mis-resolved date `MAX_START_LAG_MINUTES` catches. That repair is narrow on purpose — a past start with NO end, a fully passed window, and a sliver too short for the shortest stop all still fail. `planner.test.ts` is heavily covered (35 cases) and must stay that way — every rule above is load-bearing. (It is not the largest suite: `swap.test.ts` has 79 cases and `schedule.test.ts` 43 — verified 2026-08-08.)
- **Code-owned guarantees the model cannot skip:** an unspecified time always ships a when-question; questions are capped at 3 (vague-attached first, then when); slots are renumbered dense; question ids are made unique; the immediacy, all-day and WEEKDAY floors read the RAW prompt and override the model. The weekday floor exists because live runs had "plan my saturday" landing on Friday: which date a named weekday falls on is a fact, so code re-derives it and shifts the window as a unit, keeping the stated wall-clock hours. It corrects facts, not readings — it abstains on a competing calendar phrase and leaves a correct resolution alone.
- **A stated range rolls as ONE unit.** Both ends belong to the same day, decided by the END (a window whose end has passed is tomorrow's; one underway is still today's). Rolling each end independently produces an inverted window that the validator rejects, silently downgrading a good prompt to the fallback — and it is invisible to any test with a fixed `NOW`, which is why `fixtures.test.ts` sweeps all 24 hours.
- **Durations: the LLM estimates, code bounds.** The planner proposes `estimatedMinutes` per activity; `selectVenues` REFINES it against the venue actually picked (folded into the existing select round-trip via a `minutes` field, not a second call — an extra round-trip per plan is real latency). Both are clamped to 15–360; the resolved value rides ON the selection as `plannedMinutes`, like `priceLevel`/`description`/`currentOpeningHours`, so nothing downstream re-derives it. `buildSchedule` prefers the stop's own duration and falls back to `DURATION_TABLE` — which must NOT be deleted: swap, reroute and recovery slots create stops without a planner pass, exactly like `home.ts`'s `HOME` constant. Only the BASE is the model's to judge; the buffer stays the table's scheduling margin.
- **Window validation (code owns the arithmetic).** When the planner states an `endISO`, `checkWindowFit()` re-checks the plan against it AFTER real travel legs are folded in — the concrete case the architecture rule names. Inside `WINDOW_OVERRUN_TOLERANCE_MINUTES` (30) nothing happens: a stated window is rough intent, and dropping a whole activity to recover fifteen minutes is the worse harm. Past that, the trailing stops that don't fit are dropped and NAMED in the banner (`windowOverrunMessage`); if not even the first fits, it fails loud (`windowTooTightReason`). A large unfilled gap is the planner under-filling — logged as `[window-fit]`, never filled in code, which would be a second planning mechanism in the wrong language.
- **Questions are LLM-authored, one round.** Answers go back for a SECOND planner pass rather than being merged client-side — folding free-form answers onto searchQueries and a time intent is the same judgment the planner just made, and doing it twice in two languages is how the old rule table grew. Skipping always still plans.

## Non-negotiable invariants
- **Reroute floor_time:** floor_time = max(now, active stop's end). Stops at or before floor_time NEVER change. Locked stops never change. If any change violates this, STOP and flag it — do not paper over it.
- **Reroute blast radius + anchor:** a reroute replans ONLY stops strictly downstream of the disrupted leg (timed positions ≥ legIndex+1); stops upstream of the break keep their COMMITTED times even when the outing hasn't started. The replanned chain departs at max(floor, previous kept stop's committed end) — never re-derive the schedule from `now`; the clock only wins once it has overtaken the plan. `anchor_time` (that departure instant) is what the banner shows; `floor_time` stays the guarantee value. The `[reroute-apply]` log prints committed starts, floor, affected set, and post-reroute starts — check it first when a reroute moves the wrong stops.
- **Locked ratchet:** a stop locks when active or past, and never unlocks — survives completion and backwards time travel.
- **Keep-on-missing-data:** never drop a venue for missing data (no price, no hours, no rating = keep). Applies to every filter rule. ONE exception, and it is not a filter rule: a PRICE-DIRECTION swap ("fancier"/"cheaper") never hands back an unpriced venue AS its result — see the swap section. The rule forbids DROPPING a venue for a missing field; it does not require answering a price question with a venue that has no price. Ordinary swaps and every filter still see those venues untouched.
- **ID validation on select:** the LLM picks by venue ID only; invalid ID → one retry with correction → highest-rated fallback flagged. It can never invent a venue.

## Reuse, don't fork
The replan reuses the real pipeline via `searchPlaces.ts` and `selectVenues.ts` (callable cores; the routes are thin wrappers). Reroute imports these — never fork a parallel replan path, or fixes drift.

## Standing policies
- API keys server-side in `.env`, one per Google service, restricted in Cloud Console. Two things are deliberately browser-side (`NEXT_PUBLIC_`): the Maps JS key, protected by referrer restriction, and the six `NEXT_PUBLIC_FIREBASE_*` values, which are client config by design rather than secrets (Firebase enforces access through Auth rules and authorized domains, not key secrecy). Everything else stays server-only — the Geocoding key in particular has its own `GOOGLE_GEOCODING_API_KEY`.
- Unstated times resolve via CATEGORY_START_DEFAULTS (dinner 19:00, brunch 10:30, etc.) before falling to next-full-hour. Past times roll forward to next day. This is the fallback for callers that do NOT come through the planner (swap, reroute, legacy stored plans); the planner's own resolved start wins outright when present.
- One resolved `startInstant` is shared by scheduling, hours filtering, and the weather gate — they must never diverge.
- **Per-plan timezone (zone-aware everywhere):** every plan carries one resolved IANA zone (`itinerary.timeZone`, from `zoneFromLatLng` on the geocoded start; default `America/Toronto`). ALL scheduling math ("now"/"today"/which-hour), the hours filter's day-of-week + hour, and every display label render in THAT zone — never the server's wall clock, never the viewer's browser, never unconditionally Toronto. Zone math lives ONLY in `app/lib/zoneTime.ts` (luxon + tz-lookup, both offline); do not hand-roll `Intl.DateTimeFormat` parsing — that caused prior TZ/meridiem bugs. `toZonedISO(d, zone)` is byte-identical to the old Toronto formatter for the default zone, so Toronto plans are unchanged. When threading a new time computation, pass the plan's zone (`itinerary.timeZone ?? DEFAULT_ZONE`); `wallClockParts().weekday` is 0=Sun (NOT the day-of-month `day`). Note: `TZ=America/Toronto` on the server no longer drives scheduling (it's per-plan now) and `new Date()` is an absolute instant, so the server's zone is irrelevant to scheduling. **The `usableByHours` exception previously recorded here is RESOLVED** (corrected 2026-07-31): the swap engine's default availability check now judges the instant on the venue's local clock via the shared `isOpenAtInstant`, takes a `timeZone` parameter, and both call sites (`swap.ts:705`, `swap.ts:1577`) pass the plan's zone. No production path reads `getDay()/getHours()` any more — the only remaining occurrence is the comment in `swap.ts` describing the old behaviour, plus `MOCK_RAIN_HOUR` in the mock fixtures, which is test data. FLAGGED, not resolved: DEPLOY.md still requires `TZ=America/Toronto`, and this was its stated justification. Re-evaluate that requirement on its own evidence before dropping it — this reconciliation did not audit DEPLOY.md's other reasons.
- Transit legs get a +5 min delay margin; that buffer is separate from stop-duration buffers. A leg relabels as walk (no margin) when it's short (<400m), or when walking beats transit+margin AND the walk is ≤30 min (`MAX_WALK_LABEL_MIN`), or when walking is at least twice as fast as transit (broken-transit escape hatch, any length) — a 75-minute walk must never be presented over a similar transit ride. A hop below the stricter 250 m haversine threshold skips TRANSIT upstream and requests WALK only. If both modes fail, the fallback stays `unknown`, uses a 1.35× detour allowance plus 20% uncertainty (minimum 5 min), and draws no map route. Every displayed WALK route carries the provider-required visible/accessibility caution.
- **"BOARD" NOW MEANS BOARD (2026-08-13).** The strip's leg line used to print `boardISO: stop.end_time` / `arriveISO: next.start_time` — the dwell end and the next stop's start, i.e. the padded door-to-door span, with the first instant MISLABELED "board". You do not board the train when you stand up from dinner, and that mislabel is why the numbers looked like they did not add up: the walk, the wait and every transfer were folded invisibly inside one span. The leg now shows FOUR instants — LEAVE (dwell end) → BOARD (provider) → ALIGHT (provider) → ARRIVE (next start), a board/alight pair PER RIDE — and the scheduler's two instants are named `leaveISO`/`arriveISO` in `StripLeg`. `boardISO` on a StripLeg no longer exists; the name now belongs to the provider's instant on `TransitSummary`.
- **WHEN the breakdown shows is `shouldShowTimeline` (2026-08-14), and it is `isActiveNow || isSelected`** — you are ON this leg right now, or you tapped it. The "board times / hide times" disclosure it replaced is GONE (with its manual-open state): a control the traveller operates for information they either just asked for or are standing in the middle of. The two gates in FRONT of the OR are load-bearing and must stay in that order — non-transit and "no usable timeline" both refuse first, so neither the clock nor a tap can conjure times that were never published or that no longer belong to the leg; the single-line and staleness fallbacks are reached exactly as before. `legUnderway` judges the leg's window half-open `[leaveISO, arriveISO)`, the same shape `deriveStopStatus` gives a stop; an unreadable window is never underway. The compact card is the leg's identity + the TOTAL alone (`"85 min"` — no transfer count, no `incl N buffer`); a multi-ride leg's identity is the routes in riding order, not a transfer count — see the badge bullet below for what "identity" renders as. **"Now" DOES NOT TICK** — no interval exists anywhere in the app, statuses are derived server-side per read — so an active leg opens on the existing render cadence, not by itself on a timer. Do NOT add one. The instant is `page.tsx`'s `displayNow` (dev sim clock when set, real clock otherwise — the same instant the store was asked for), threaded into the strip as `now`: one clock, or the leg check and the "now" pill disagree the moment anyone simulates time. The leg summary is a native button (`.lstrip__legselect`) with the timeline as its SIBLING, mirroring `.lstrip__select`; a transit leg with no usable times gets NO button at all.
- **The ROUTE BADGE sits where its route is named, and the number is never printed twice (2026-08-14).** The strip's badges used to stack in the card's top-left corner while the same routes were spelled out in the text below (`"091 Bayview → 1 Yonge - University"` under an 091 and a 1 circle). The stack is GONE from both states: the badge is inline in the collapsed title with the PLACE beside it (`[091] Bayview → [1] Yonge - University`), and inline in the expanded timeline on that ride's own BOARD row — you get on a route where you board it, so leave/alight/arrive get an empty rail cell and every row's word stays on one column. The split is pure and lives in `transitBubbles.ts`: `linePlace`/`lineBadges` take the designation off the FRONT of the published name (first two tokens only — agencies write both "091 Bayview" and "Line 2 Bloor–Danforth"), and **the test is what the CIRCLE prints, not what the agency published** — an initials badge ("Lakeshore West" → "LW") or one clipped to circle width ("EXPRESS" → "EXPR") is not in the name, so the NAME STANDS WHOLE rather than lose a word the badge only half-says. Degrades by leg shape at that one seam: transfer → badges with arrows between, single ride → one badge and no arrow (the `· N stops` suffix still only when one ride owns the leg), walk / `unknown` / a pre-segments stored plan → no rides, so no badge and the mode glyph as before. Colour is still `seg.color || var(--ink)` on the same `.lstrip__bubble` base class. **Laid out in ORDINARY TEXT FLOW** (`vertical-align: middle`), NOT flex rows — a flex row gives a name only the sliver left beside its own circle and breaks "Universi/ty" in a 118px card. The circle is `aria-hidden` with the published name in an `sr-only` span beside it, so what a screen reader hears is unchanged. The rows find their badge by `TimelineRow.rideIndex`, never by matching the line's NAME — a leg can ride the same line twice. The MAP's leg-label pills are untouched and still stack (`groupBubbleUnits`, `leglab__*`): a label has no room for prose.
- **The provider's board/alight instants and stop coordinates are FREE, and they are DISPLAY ONLY.** `routes.legs.steps.transitDetails` is a PARENT path in the field mask, so `stopDetails.departureTime`/`arrivalTime` and each stop's `location.latLng` already arrived on every transit response — `extractTransitSegments` read `.name` and dropped them. They now ride on `TransitSummary` as `boardISO`/`alightISO`/`boardLocation`/`alightLocation` (optional AND nullable: absent on every pre-2026-08-13 stored plan, null when the agency publishes none). **No field-mask change, no extra call, no cost — and NOTHING scheduling reads them.** `buildSchedule` still runs on `leg.totalMinutes`, `checkWindowFit` is untouched, and every computed time is byte-identical. A provider board time is the timetable for the instant the leg was PRICED at; re-deriving the schedule from it would make a forecast into a commitment.
- **The STALENESS rule is monotonicity, and it lives in `app/lib/transitDetail.ts`.** A swap/reroute re-fetches the legs it moves, but a leg it does NOT move keeps provider times anchored to the old departure while its window shifts underneath. `buildTransitTimeline` therefore renders only when leave ≤ board₁ ≤ alight₁ ≤ … ≤ board_n ≤ alight_n; any violation, any missing instant, or a PARTIAL multi-ride leg returns null and the card falls back to the single `leave · arrive` line. No tolerance constant, and no second definition of "stale". What it shows is labelled SCHEDULED, never promised. Known residual: a plan that shifted EARLIER can stay monotone and still be slightly stale; the failure is conservative (the times sit inside the window) and a fuzzier rule would cost more than it saves.
  - **THE CHAIN STOPS AT THE LAST ALIGHT — `arrive` DOES NOT BOUND A PUBLISHED INSTANT (corrected 2026-08-14; it used to, and that was the bug).** `arrive` is `leave + totalMinutes` and `totalMinutes` is the provider's route DURATION plus our margin — and that duration is measured from the moment the traveller starts MOVING, not from the departure instant we asked about. **The platform wait is outside it.** Verified against the live Routes API: a leg priced for a 00:00 departure boarded at 00:15:28 and reported 77 minutes, so the last alight landed 5.4 min PAST the scheduler's arrival on perfectly fresh data. Bracketing published instants with that forecast is a category error, and it suppressed the whole breakdown on real long cross-town legs (measured: 2 of 9 at an 8pm anchor, 0 of 12 at 7pm — it tracks how sparse the service is, so the worst cases are late nights and the longest legs). Three of the four instants are FACTS (leave is the instant the leg was priced at; board/alight are published); ARRIVE alone is a forecast, so **when the forecast contradicts a published fact the FORECAST yields** — the arrive row is dropped, the timeline ends at the last alight, and no row is ever out of order. The tail guard is now COHERENCE, elapsed-vs-elapsed: `alight_last − board₁ ≤ arrive − leave` (fresh data always clears it; an inverted window never does). **Mock e2e cannot catch any of this** — `mockLeg` boards at `departure + MOCK_WALK_TO_STOP_MIN`, i.e. it models a ZERO wait, which no real agency has.
  - What the contradiction really means is that the PLAN under-budgeted that leg by the wait. That is a SCHEDULING question and is deliberately NOT fixed here: `buildSchedule` runs on `totalMinutes`, and re-deriving it from a provider board time is the one thing this whole slice forbids. Flagged, not done.
- **Transfer markers are drawn at a REAL coordinate or not at all.** `transferPoints` (same module) pairs ride i's alight with ride i+1's board and takes the alight coordinate (the name follows whichever coordinate was used), falling back to the next ride's board coordinate; with NEITHER published it emits nothing. Deliberately NOT `midPx` — the leg midpoint is fine for a leg CAPTION but a transfer is a place, and averaging two stops would invent one. Rendered as `.mk--transfer` divs in the existing `.ov-layer` at `px(lat,lng)`, mirroring `legLabels`; hollow ring + change glyph, `z-index: 3` so a stop marker wins an overlap, and no `--live` anywhere.
- **`pathSegments` IS THE GEOMETRY THAT FEEDS THE MAP, and it is DISPLAY ONLY (added 2026-08-16, Transit B piece 1).** `encodedPolyline` is the whole leg as one string with no seams; `pathSegments` is the same leg as the provider's own STEPS in travel order — `{ mode: "walk" | "transit"; encodedPolyline: string; color?: string | null }[]` on `TravelLeg`, beside `transitSegments` and independent of it (that field carries the rides' times and colours, this one their shape). It cost THREE field-mask additions (`routes.legs.steps.polyline.encodedPolyline`, `.travelMode`, `.staticDuration`), all Essentials-tier against an already-Pro request, so the SKU should not move — INFERRED from Google's docs, not measured; one live billing line is still worth checking. **`travelMode` decides the mode and nothing else does** — a step we do not recognise is skipped, never guessed from whether `transitDetails` happens to be present — and `color` is read from `transitLine.color`, the SAME field the strip's badge reads, so a line and its bubble can never disagree. **NO GEOMETRY, NO SEGMENT**: a step without a polyline produces nothing, an empty string is not geometry, and a leg with no drawable step carries NO key (never `[]`). **`staticDuration` is requested and deliberately NOT STORED** — it is the one number here that could be mistaken for a scheduling input, and the shelved "the plan under-budgets the platform wait" finding stays shelved. `schedule.ts` is untouched and `buildSchedule` still runs on `totalMinutes` alone. The steps are walked ONCE (`readSteps`); `extractTransitSegments` is now an accessor over it and its output is unchanged, which is what the mock fixture imports. Geometry always comes from the route its NUMBERS came from — a walk-relabeled leg draws the WALK response's steps. **The two validators are deliberately asymmetric**: the server SANITIZES (a malformed segment is dropped, the leg survives — a decoration must never cost someone a stored plan) while the browser REJECTS like every other guard there, since by then the server has already sanitized. Both cap a segment at 4096 chars and a leg at 128 segments, written twice because `clientPayloads.ts` cannot import server modules; **the cap is a FILTER that deletes rather than errors** (the `max_price` lesson), so it was probed — the longest real step measured 636 chars on a 21-step cross-town journey. FLAGGED, not fixed, and pre-existing: `parseScheduledStops` validates NOTHING on `stops[].travelToNext`, so the stop's copy of a leg escapes both this sanitization and Build A's ride checks (whose coordinates become map markers), and `rebuildLegs` would copy it back into `legs` on the next mutation — reachable only by a hand-crafted POST, and the browser's own guard refuses such a plan on read.
- **TRANSIT B PIECE 2 DRAWS RIDES, NOT GUESSES (added 2026-08-17).** When a transit leg carries `pathSegments`, `ItineraryMap` walks them in provider order, ignores every walk step (Piece 3 remains deferred), decodes each transit step independently through the ALREADY-LOADED Maps geometry library, and creates one native primary polyline per usable ride. The primary stroke uses the provider's six-digit `transitLine.color`, falling back to the map's canonical `INK = "#2E6F8A"` when that value is absent or unusable. Missing, throwing, empty, one-point, non-finite or out-of-range geometry draws NOTHING for that ride and never falls back to the whole-leg string or an endpoint line; one bad step cannot suppress a later good one. A pre-Piece-1 transit leg with NO step array may still draw its real whole-leg encoded fallback, but transit with no provider geometry draws no line. Plain whole-leg WALK rendering stays solid ink and its endpoint fallback stays intact. **ROUTE COLOURS WIN OVER `--live`:** a changed destination still marks its inbound LEG, but every usable ride in that leg gets a wider, low-opacity halo in its OWN route colour underneath the unchanged primary stroke; legacy transit and plain walk use the same non-colour halo language. The renderer never substitutes chartreuse for route geometry. Every effect invocation owns and detaches only the overlays it created on rerender, map-state change and unmount, so async/Strict-Mode cleanups cannot leak duplicates or delete newer lines. Native polyline coordinates, marker projection and coordinate-only fit bounds remain separate and unchanged.
- **Location (multi-city):** the CITY and STARTING ADDRESS are plain text inputs on the empty state — resolved by the purpose-built Geocoding API via `POST /api/geocode` and its dedicated server-only `GOOGLE_GEOCODING_API_KEY`. City results must be locality-typed. Multiple valid matches enter `recovery.mode: "geocode"` for an explicit formatted-address choice; never take provider index zero. The chosen formatted city rides on `parsed.city` (app-injected, never LLM-inferred) so Places/swap/reroute searches stay disambiguated; the chosen start is stored as `itinerary.home` and everything home-related reads `itinerary.home ?? HOME` (the Chestnut default exists ONLY for pre-multi-city itineraries and tests). Weather takes `?lat=&lng=`. The parse's `location` field is a neighbourhood WITHIN the city, never a city. Never silently fall back to Ossington/Toronto for a user-entered city. Real location services / geolocation remain deliberately unbuilt — plain queries only.
- **A START MAY SIT OUTSIDE THE CITY, and the rule that decides is a DISTANCE** (2026-08-13; this bullet used to say addresses are "objectively checked against the resolved locality/administrative region/country" — the locality half is GONE). People commute in, so `judgeStartProximity` (pure, `geocode.ts`) measures haversine from the geocoded start to the city's **LOCATION** — never its viewport, whose size varies far too much between cities to compare against — against `MAX_START_DISTANCE_FROM_CITY_METERS` (75 km). Past it: `geocode_far_from_city` (422), naming the city. **The country check stays hard and first** (`geocode_wrong_country`), and `geocode_incomplete_address` is untouched. **The region check is SECONDARY and that word is load-bearing:** a province/state mismatch refuses only beyond `SAME_METRO_METERS` (25 km), because inside that radius every cross-region address is a real metro suburb (Gatineau→Ottawa 2 km, Jersey City→New York 10 km) — a hard region drop re-creates the locality bug one field over. Two traps, both found by a LIVE run and neither visible to a unit test: (1) `buildGeocodeUrl` must NOT append the city's locality to the address text — "12 Elm St, Mississauga" + ", Toronto" is self-contradictory and Google answers it by relocating the result or flagging `partial_match`, so the validator never sees the address it is judging; region + country + the viewport bias are what disambiguate. (2) `parseResult` takes `administrative_area_level_1` OUTRIGHT, falling back to level_2 only when there is no level_1 — asking for both at once returns provider order, and for Toronto level_2 is also spelled "Toronto", which put the city's own name into the suffix AND the region check. Do not merge those two lookups again. Dropping the locality rule STRENGTHENS the ambiguity panel: an out-of-city address and its in-city lookalike now both survive to be chosen between. This 75 km cap is also the app's ONLY distance cap on a start — without it a 200 km typo becomes a silent multi-hour home leg, since `getSingleLeg` estimates any distance. **Mock e2e cannot reach ANY of this** (`mockGeocodingResponse` returns fixed Chestnut coordinates for city and address alike, so a mock start is 0 m from its city); `geocode.test.ts` carries it, 16 cases, boundary pinned both sides via the rule's own haversine run backwards.
- **The CITY, not the start, is the sample point for weather and the timezone** (2026-08-13, with the change above — they were the same point only while a start had to be in the city). The forecast gates OUTDOOR VENUES and those venues are in the city, so a suburb's rain answers the wrong question; the zone drives every scheduled time and label, and 75 km can cross a zone boundary. `planZone` is the city candidate's and is never reassigned from the address. The city centre rides on the parse as **`parsed.cityCenter`** — app-injected beside `parsed.city`/`parsed.home`, never LLM-inferred — so `swap.ts`'s `weatherFor` and `reroute.ts`'s `weatherOrigin` read it too, each falling back to `home` for plans made before it existed.
- **Places call/cost boundary:** the complete Text Search mask is intentional: identity/location, business status, hours, rating, price, stop-card description, and provider-structured constraint evidence all have deterministic consumers before selection. Named categories cost one call (two late-night variants at most), the general pool five, and eight categories cap an attempt at 16 calls. Identical query+type work deduplicates only inside one attempt. Never cache full Places content across attempts (provider-policy and hours-freshness boundary); place IDs are the long-lived identifier. A discovery→Details split is not a cheaper fact-safe shortlist under the current field/pricing shape.
- **Persistence seam:** routes access the itinerary store ONLY via `loadItinerary`/`saveItinerary` (store.ts). KV env vars set → Upstash Redis REST is the source of truth (always read Redis, always write back after mutations — `withStatuses`' lock ratchet mutates even on GETs and refusals); unset → the in-memory Map (dev/e2e). ## Fail-loud surface (operational notes)
`app/lib/planGuards.ts` is THE surface for bad input — every degenerate/impossible/contradictory prompt must land there (or in `resolveStartTimeChecked`'s malformed-input messages) with a reason + suggested fix; an empty map or a borrowed error from another branch is the bug. Guard order in `runPipeline`: degenerate prompt (pre-model) → unparseable parse → contradiction → [clarify questions] → malformed time input → all-pools-empty net → unmet constraint → PARTIAL-failure recovery (the interactive panel below). **There is no plausibility gate** (removed 2026-07-27): an unusual hour is planned, and the objective hours filter decides what is genuinely open — "nothing's open at 3am" is a fact, "brunch isn't plausible at 3am" was an opinion. A hard refusal string is the right answer only when there's no real choice to offer; once there IS one (a weather block, a partly-empty plan), it belongs in the recovery panel instead — see the next section. Constraints are enforced in `selectVenues`: no evidenced candidate → `id:null + unmet_constraint` (valid, no fallback), and a code-side hedge guard converts "worth confirming / may accommodate" picks into the same failure — never suggest a venue while telling the user to verify a constraint. `priceLevel` + `description` ride ON the stop (Selection → SelectionLike → ItineraryStop, set by swap's buildStop/finalize too); the strip must read the stop's own fields before any pools lookup, which goes stale after swaps.
- **EVERY identity field must move with the venue, and `currentOpeningHours` is the one that was missed** (fixed 2026-08-15). `page.tsx`'s arrival-time ADAPT path (the try → adapt → notify ladder in `runPipeline`) spreads `...s` and then overrides `id`/`name`/`rating`/`priceLevel`/`description` — but not the hours, so an adapted stop carried the REPLACED venue's opening hours for the rest of the plan's life. That is not cosmetic: `placeOf(stop)` reads the stop's own field, so every later availability check judged the new venue against the old one's clock. A plan whose dessert adapted to a late-night bakery still claimed a 9 PM close, and any later re-timing that moved it earlier looked like arriving after closing — which the tail reflow answers by SUBSTITUTING THE VENUE AGAIN. Reachable from the swap engine too (`resettleTail` reads the same field for the same purpose); found while building remove-stop, because closing a gap is the change most likely to move a stop earlier.

## Shipped — interactive recovery panel (operational notes)
ONE component in `app/page.tsx` (`recovery` state, a discriminated union on `mode`), three triggers (a fourth, `time-gate`, was removed with the plausibility gate on 2026-07-27). Never build a parallel panel for another case — add a mode.
- **`mode: "geocode"`** — the purpose-built geocoder returned more than one valid typed city or in-city address. Show the formatted-address candidates and resume with exactly the chosen candidate; do not repeat the ambiguous request or select index zero.
- **`mode: "empty"`** — partial failure: some categories picked, ≥1 pool came back empty. `partialEmptyCategories` detects it (all-empty stays on `noVenuesReason`, never routes here). - **`mode: "weather-gate"`** — a category was emptied by the weather gate specifically, while others survived. The ALL-weather-blocked path keeps `weatherBlockedReason` untouched.

## Shipped — swap engine (operational notes)
Per-stop swap (`app/api/itinerary/swap.ts`, `POST /api/itinerary/[id]/swap`): user taps an UPCOMING stop, types a complaint, the engine acts on intent — VENUE (replace, hold slot), TIME (move the slot), DURATION (change how long), or CONSTRAINT (re-search). Distinct from reroute (external disruption → downstream replan). `floorTime()` shared from `store.ts` by both engines.
- **Time / duration swaps**: `parseTimeExpr` (relative "an hour earlier" = -60, absolute "after 8" = 20:00, meridiem anywhere "6pm" = 18:00, bare "3:30" = 15:30 — assume PM only for meridiem-less times; a number owned by a duration unit, "make it 2 hours", is never a clock time) and `parseDurationExpr` (absolute "stay 2 hours" = 120, relative "stay longer" = +30) are the deterministic floors under the LLM interpret — arithmetic never depends on the model. Merge rules: a locally-parsed ABSOLUTE time always beats the model's; an EXACT local relative beats the model's; only a VAGUE local relative ("a bit earlier") accepts model refinement, and only same-sign ≤3h — garbage deltas must never drift a stop across the day. A phrase with BOTH halves ("start at 6pm for 2 hours") routes to time and applies the duration alongside via the shared `resolveNewTotal` bounds — neither half is ever dropped. A time-swap moves the slot, never resizes it, and a VENUE swap holds the whole slot, length included: the stop's customized `durationMinutes.total` is the source of truth everywhere a swap keeps the same category. It resets to the (new) category default only when the stop changes KIND — a category-changing research swap, or an engine-adapted replacement venue. The `[swap-apply]` log in `swapStop` prints intent + before/after start/total — check it first when a swap changes the wrong field. Both call the reusable **try → adapt → notify** ladder `resettleTail` (shift/reflow the tail, keep a downstream venue if still open at its new arrival, else re-search an equivalent, else fail loud). Plan-then-commit: a failed resettle leaves the itinerary untouched. Duration guards: floor at the category's realistic minimum, cap 6h. `buildStop` takes a `durationOverride`; `resettleTail`/`commitTail` carry each stop's `totalMinutes` so a custom duration survives a later reflow. Keep `resettleTail` generic — it's the shared spine of time + duration (and future) swaps.
- **Price-direction swaps ("fancier"/"cheaper") rank in CODE, or refuse.** `parsePriceDirection` reads the RAW refinement (never `interp.budget`, which is the model's echo) and `rankByPriceDirection` keeps only candidates STRICTLY past the current stop's own `priceLevel` — the same shape as the `CLOSER_PATTERN` distance block, for the same reason. Same-tier is not a move: allowing it is what made repeated "fancier" swaps ping-pong A→B→A. `ranked` is the WHOLE eligible set. An unpriced venue is reported but never presented as the answer (the keep-on-missing exception above): it cannot be shown to move in the requested direction, and the earlier `ranked.length > 0 ? ranked : unpriced` fallback is exactly how a park or attraction — a category Places prices for nobody — returned an arbitrary venue as "fancier". Two refusals, and the difference is a fact not a tone: `comparable` false (NO candidate priced) can only say "can't compare prices", because "it's already the priciest" is a claim about data nothing here has. Best effort survives in one place only — no price on the CURRENT stop while candidates ARE priced ranks them most-extreme-first rather than refusing. Price words are also stripped from `constraints` at all three producers (localFallback / judge / search): `buildQuery` splices constraints into the Places query verbatim and `constraintEvidence` proves them from six provider booleans, so a leaked "nicer" is both query noise and a permanent unmet_constraint refusal.
- **Category-CHANGING swaps ("board games instead") ride the existing venue/constraint intents — no new intent, no client-contract change.** The model's `category` is its ANSWER and `path` is only its classification, so ONE effective `path` is derived once (`interp.path === "research" || changesCategory`) and drives the pool, the search parse AND the path reported back — deriving it per consumer is how a swap searches a new kind through the refilter parse and then tells the client it narrowed the old pool. The stop takes the NEW kind's default length (honest length, not the old slot's — `finalize` already did this); `resettleTail` absorbs it downstream, and a length that strands a locked stop REFUSES with the collision named. (Pushing later stops back to make room SHIPPED on 2026-08-08 — see the slot-push section below. It applies to the INBOUND-unreachable case; a length that strands a LOCKED stop still refuses, because a locked stop is never movable.) **The category is stripped from `constraints` at the same place price words are**, and for the identical reason: a KIND of place is unprovable from `constraintEvidence`'s six booleans, so a leaked one makes `placeMeetsAllConstraints` false for every venue that exists — a permanent unmet_constraint refusal. The strip is an EQUALITY test against the new category (via the judge's own `normalizeConstraint`), deliberately NOT a keyword list: "patio" is a genuine provable constraint and any list broad enough to catch "board games" would eat it. Refusals name the REQUESTED kind, with the right article ("a board game cafe" vs "another bar"). The same-category guardrail for "something different"/"surprise me"/"somewhere else" lives ONLY in `REFINE_SYSTEM` and is pinned twice — an engine case (a same-category interpretation must stay on `refilter`) and a case asserting the prompt still names those phrases. Neither pins the live model; a live probe of the tuned prompt classified 10/10 correctly (2026-08-07).
- **EVERY inbound leg is priced at the instant you actually DEPART, the home leg included (fixed 2026-08-14).** `planAnchorInbound` passes `prevStop.end_time` for every leg that has a previous stop; the HOME leg has none and used to pass `undefined`, which hands the provider "now". Re-price a 7pm plan at 9am and the ride comes back on this morning's timetable — the MINUTES are the wrong time of day's, and the board/alight instants land hours before you leave, so the staleness guard refuses them and the strip's home leg loses its breakdown for the rest of the plan's life. Home-leg-only by construction, which is exactly how it presented: the FIRST leg, and only the first, stopped opening after any swap that touched stop 0. `homeDeparture()` is the anchor's start less the stored home leg — the same subtraction the strip renders as "leave by" — bootstrapping the new leg's departure from the old leg's length the way `getTravelLegs` accumulates; `anchorStart` is the fallback when no home leg is stored. **`reroute.ts` never had this** (it always passes `new Date(cursorMs).toISOString()` and never touches the home leg); the initial pipeline never had it either (`departureTime: startISO`). Do not let a third caller re-introduce it.
- **Availability seam**: `SwapDeps.isUsableAt(place, when, category)` is the ONE "is this venue usable then" check (default = objective hours, keep-on-missing). A real availability/reservation API replaces that function body only. It is asked TWICE — at arrival and at the last moment actually spent at the venue — so a venue that closes MID-SLOT is no longer a legal answer (a coffee shop closing at 9:30 used to fill a 9:00–10:00 slot, because `isOpenAt` is a single-instant check and every caller passed the start). Two boundaries are deliberate and load-bearing: the far end is OCCUPANCY (`total` minus the table's buffer — the buffer is scheduling margin, and judging against it adapted a bar closing at 22:00 away from a 20:55–21:55 stop), and it lands one minute inside the end, because occupancy is [start, end) and `isOpenAt` reads the closing minute as closed. `usableForProposal`'s `slotMinutes` is REQUIRED so no new call site can silently keep arrival-only; pass `ARRIVAL_ONLY` explicitly for a downstream stop this swap does NOT move — the initial pipeline's `filterPools` is still arrival-only, so re-judging an untouched stop here lets an unrelated swap silently re-kind stops the user never touched. **FOLLOW-UP, not done:** that planner-side asymmetry belongs in `filterPools`, not in a swap.
- **The SLOT PUSH — a replacement too far to reach moves its own slot later, and the tail with it.** `finalize`'s `startISO` is the slot's REQUESTED start, never a guarantee. `planAnchorInbound` no longer collapses "can't get there by then" into the same `null` as its six genuinely-unverifiable cases; it returns `earliestStartMs` (previous stop's committed end + the REAL leg) as a FACT and each caller sets policy. `finalize` takes `Math.max(requested, earliest)` — that one operator IS the never-earlier guarantee, and a reachable start leaves the slot byte-identical to the old path — then runs the UNCHANGED `resettleTail`, which already owned the cascade. **The route is planned BEFORE the usability check now**, because "open for the whole slot" cannot be answered until the slot is resolved.
  - **TIME and DURATION swaps still REFUSE** (`reachesStart`). A time swap NAMED that time; landing the user at 8:20 because 8:00 was unreachable answers a different question. A duration swap is not moving the start at all.
  - **The FIRST timed stop never pushes**: with no previous stop `earliestStartMs` IS the requested start, because the origin is home and a home departure is not a committed boundary. Today's behaviour, unchanged and now explicit.
  - **HARD limits are inherited, not re-implemented** — that is the whole design. Closing time (`usableForProposal`, incl. the open-at-END check, which every pushed stop gets because `movedByThisSwap` is true for it), locked/past stops, and real-leg recomputation all live in `resettleTail` and were not touched. A stranded stop REFUSES and NEVER prompts: consent cannot open a closed door. The refusal keeps `resettleTail`'s own message (which names the stop and the instant) and prefixes the push context.
  - **The SOFT limit is the one net-new constraint: `itinerary.plannedEndISO`.** Nothing enforced the user's stated end after a swap before — `checkWindowFit` runs once, in `page.tsx`, against a planner result the browser was still holding. The instant is now persisted at creation (`storeItinerary` → `parseOptionalInstant` → `createItinerary`), because it outlives the request that knew it. **ABSENT MEANS NO CEILING** — most plans, every pre-2026-08-08 plan — and the push then runs as late as real hours allow. Code must never invent one.
  - **Past the stated end it ASKS, it does not refuse.** `SwapResult` gains an optional `confirm: EndTimeConfirm` on the `swapped: false` arm — present ⇒ a QUESTION, absent ⇒ a refusal. `swapped` stays false, so the route reports `changed: false`, no CAS runs, and declining is free by construction. Accept re-sends `endTimeAccepted: true`, which skips ONLY that guard and re-runs the swap from scratch (no cached proposal — the engine holds no per-request state; `version` still rides along, so a plan that moved underneath 409s). The tolerance is the SHARED `WINDOW_OVERRUN_TOLERANCE_MINUTES` (30), deliberately not a second number: two definitions of "past the stated window" is how creation silently accepts 25 minutes while a swap interrupts over five.
  - **The "5 attempts" in `resettleTail` is RETRIES-PER-STOP, not cascade depth** (verified 2026-08-08) — it iterates `findReplacement` candidates for ONE stop. The cascade is `for (k = anchorPos + 1; k < timedIdx.length; k++)`: the whole tail, unbounded, terminating at a locked stop or the end of the list. There was no artificial ceiling to raise.
  - **UI**: `SwapEndTimeDialog.tsx`, mounted from `page.tsx` beside `StopItineraryDialog` and reusing its `.stopdlg` language. Decline is the safe default at every level (escape, initial focus, and nothing written server-side). `doSwap(endTimeAccepted)` re-runs the same refinement. The pushed stop now gets its OWN strike-through, read by INDEX rather than out of `oldById` — that map is keyed by venue id and the venue is exactly what changed.
- **UI**: the swap prompt is inline under the selected strip card (`ItineraryStrip` `SwapInline`), upcoming-only; reuses the reroute reflow (chartreuse card/time accents keyed by venue id; route geometry uses its own colour plus a halo). The map's projection probe defers its `setState` to rAF (never call setState inside a Google `OverlayView.draw()`).

## Shipped — remove a stop (operational notes)
Per-stop removal (`app/api/itinerary/removeStop.ts`, `POST /api/itinerary/[id]/remove`): the user selects an UPCOMING stop, arms an inline control, confirms, and the stop is spliced out while the rest of the day re-times around the hole. The THIRD mutation on an itinerary and deliberately the smallest — it only DELETES.
- **IT REUSES `resettleTail`; THERE IS NO SECOND CASCADE.** Removing stop N is "re-settle the tail from stop N-1", and that cascade's FIRST ITERATION IS THE BRIDGING LEG — the predecessor now travels directly to the successor, priced for real. `removeStop.ts` adds no travel arithmetic, no scheduling rule and no availability rule of its own. Never fork a fourth replan path (swap / reroute / remove all share this spine).
- **The shared ladder is EXPORTED from `swap.ts`, not extracted** (decision, 2026-08-15). Fifteen symbols gained an `export` keyword — `resettleTail`, `commitTail`, `planAnchorInbound`, `commitAnchorInbound`, `homeDeparture`, `usableForProposal`, `earliestUsableStart`, `proposalLeg`, `cloneProposal`, `weatherFor`, `validLocation`, `placeOf`, `clockLabel`, `realDeps`, plus the `TailChange`/`AnchorInbound` types. Extraction to a shared module would have moved ~600 lines and ~18 interdependent helpers out of a 2379-line engine covered by a 2323-line suite; the export diff is exactly 15 insertions/15 deletions and cannot change behaviour. `removeStop` still lives in its own module, which was the actual constraint. Extraction stays available as a pure move now that a second caller exists — but it is not free, and nothing needs it yet.
- **CLOSE THE GAP, BUT NEVER TRADE A VENUE FOR IT — this is the load-bearing rule.** Later stops slide EARLIER rather than holding their times. `resettleTail` DOES NOT CLAMP: its reaction to a venue unusable at a stop's new arrival is `findReplacement`, which is right for a swap and catastrophic here — removing your 7pm dinner would silently swap your 10pm bar. So `resettleTail` takes `clampEarlierToAvailability`, **OFF for every swap path (byte-identical to before it existed) and ON only for removal**. `earliestUsableStart` walks forward a minute at a time from the proposed instant, ceilinged at the stop's own COMMITTED start, and takes the first instant that passes `usableForProposal` — the very predicate whose failure would otherwise substitute. It always terminates and is always cheap (the ceiling is where the stop already sat, so the worst case is not moving; every step is pure). **Deliberately a scan through `deps.isUsableAt`, never an "opening time" lookup** — the seam is the one answer to "is this usable then", and reading hours directly would be a second definition to drift from when a reservation API replaces it. EARLIER DIRECTION ONLY: a stop forced later (a direct leg longer than the two it replaces) has no earlier instant to protect, and the existing ladder is the honest answer. **Removing stop X may change stop Y's TIME. It must never change stop Y's VENUE.**
- **DOWN TO ZERO IS REFUSED, and the reason is a real hazard.** An empty `stops` array reads as a FINISHED outing: `nextItineraryStatus` asks `stops.every(completed || skipped)` and `[].every(...)` is vacuously TRUE → `status: "completed"` → the by-id GET clears the owner's resume pointer and archives the empty plan to history, and `isResumable` refuses it forever. The guard counts stops that have a VENUE (so a plan left with only weather-skipped slots is refused too — all-skipped trips the same branch), runs BEFORE the splice and before the forecast call, and points at "End". Down to ONE is fine. FLAGGED: removing the only UPCOMING stop beside a COMPLETED one still concludes the plan — that is genuine conclusion, not a splice artifact, and is deliberately not covered.
- **LOCKED / PAST is refused** with the same predicate `swapStop` uses. **Plan-then-commit** mirrors swap exactly: everything runs on `cloneProposal`, one `Object.assign` on the success path, refusal ⇒ `changed: false` ⇒ no CAS, no version bump.
- **FIRST stop**: no predecessor, so the origin is HOME. **The departure instant does not change** — it is the removed stop's start less the home leg that served it, read via `homeDeparture` BEFORE `commitAnchorInbound` overwrites `homeLeg`. The new first stop starts as early as the re-priced real leg allows (floored by `now`, clamped by its own opening time) and may legitimately land LATER when home is further from the second stop than the route through the first was. A locked new-first stop keeps its committed start or the removal refuses.
- **LAST stop — THE DANGLING LEG.** There is NO travel-home leg in this app: `schedule.ts` deletes `travelToNext` from the last timed stop. The hazard is the PREDECESSOR's `travelToNext`, a real leg to a venue no longer in the plan, which `rebuildLegs` would copy into `legs` and the strip would draw as a journey to nothing. `resettleTail` returns no leg in exactly that case (empty `changes`, null `terminalInbound`), which is `setOutbound`'s signal to delete both fields.
- **ROUTE: its own file, not a mode of /swap.** Structurally identical (id shape, rate limit, `updateItinerary` CAS with `expectedVersion`, ETag), but swap's body requires a non-empty `refinement` that the engine hands to a MODEL to classify, and a removal has nothing to say. Folding it in would mean inventing a sentinel phrase to put in front of the LLM, or branching the route on an absent field. AUTH follows the swap precedent — none beyond the plan id (`/swap` and `/reroute` verify no caller; only `/end` does, because it writes to a person's history).
- **UI: ARM → CONFIRM, INLINE, NO UNDO.** `RemoveControl` in `ItineraryStrip.tsx`, a SIBLING of the swap form (a button nested inside that form would submit it). Armed state lives in `StopCard` because the CARD's border turns danger-red too. "Keep" takes focus so a stray Return never deletes; Escape steps back; outside POINTERDOWN disarms (not click — the `AccountMenu` rule). Reuses the existing id-keyed reflow, which survives the splice for free.
- **`--danger` (`#A3372F`) is a token now.** The value is unchanged and was already written out TEN times (auth errors, the End control, the stop dialog, history and preferences). It means "this ends something and cannot be undone" — like `--live`, a signal rather than decoration; nothing merely emphatic should reach for it.
- **No new mock seam was needed or added** — `removeStop` takes `SwapDeps` built from swap's `realDeps()`, so `mockSwapDeps` already answers everything. A removal that had needed its own fixtures would have meant it was not reusing the cascade.

## Shipped — taste-biased planning (Stage 3B) — TUNING IN PROGRESS
The 3A profile is now spent: a signed-in user's stored taste fills the aspects their request leaves open. **The tuning is NOT settled** — the mechanism is built so iteration is prompt wording only. Do not re-plumb it to change behaviour.
- **The MODEL does the judging; code hands it background and checks the answer.** Nothing writes an `aesthetic`, a searchQuery or a constraint from a preference. `/api/parse` puts a small `preferences` object in the planner payload and `PLANNER_SYSTEM_PROMPT`'s TASTE PREFERENCES section says how to weigh it — because "does this request already state a cuisine?" is semantic. The output still goes through the unchanged `findPlanProblems` ladder. A code path that applied a preference directly would be the bug.
- **Per ASPECT, never per prompt.** A stated aspect (cuisine, vibe) wins outright; only unstated ones take the default. A preference that directly answers an open aspect RESOLVES it (a bare "dinner" + stored cuisines → `confident: true`, no craving question); one that merely tilts a still-open choice does not (style + "something to do" stays vague and still asks).
- **`plannerPreferences.ts` is pure and is the ONE place the projection lives.** A phrase table deliberately separate from `SurveyOption.label` (button copy must not change planning) and deliberately punctuation-free (`aesthetic` is prepended VERBATIM into the Places query by `buildQuery`). `none`/`other` are dropped; a profile that drops to nothing returns **null**, never `{}`.
- **The dietary trap is the one guarantee made in CODE.** `contradictionReason` fails a whole plan on "vegetarian"+"steakhouse", so a stored diet the raw prompt contradicts is dropped BEFORE the model hears it — `toPlannerPreferences` takes the prompt and filters through `dietaryConflictsWithPrompt`, which reuses the guard's own `DIETARY_VENUE_CONFLICTS`. Never re-encode those pairs. Only the conflicting diet is dropped.
  - **The TYPED cuisine (`foodsOther`) is appended to `foods` and suppressed by the SAME rule** (`dietaryConflictsWithText`), checked against each diet that SURVIVED the prompt filter AND against the raw prompt — a stored diet plus a typed "steakhouse" is two PREFERENCES, neither restated, manufacturing the same hard refusal. Only the free text is dropped. Known and accepted: it does not strip the accommodation phrasing `contradictionReason` does, so "vegan options" + a typed "seafood" over-suppresses for that plan. Free text ALONE still projects non-null; the `other` slug stays in `NON_PLANNING_OPTIONS`. The prompt separately says a dietary preference belongs in the searchQuery and NEVER in `constraints` (constraints are hard requirements the REQUEST stated) — that half is wording, and a live run has been seen to leak it; if it reproduces, the lever is firmer wording or a code-side strip.
- **NULL IS THE ORDINARY PATH.** Guest, anonymous, no Firebase (mock e2e), failed read, skipped survey → no `preferences` key, and the payload is byte-identical to pre-3B (a test pins this). No new mock seam was needed or added: `readTasteProfile` already degrades.
- **Identity from the verified token only** — `verifyCaller` then `readTasteProfile(caller.uid)`. No `?uid=`, nothing from the body, no schema change. Anonymous callers skip the read as a COST decision (hot path, known-empty answer), not as a second gate. `page.tsx` sends `authHeaders()` on `/api/parse`.
- **Invisible by contract**: no badge, no "because you like X" anywhere the user reads. The `planner_plan` log carries `personalized: true|false` — WHETHER, never WHICH.
- **Bundled in the same prompt pass: the VARIETY rules.** An un-named day gets at most one eating and one drinking stop; the caps release the moment the request names them ("dinner and drinks", "bar crawl"), and a stated activity is never dropped for variety.

## Shipped — activity-interest personalization (the 3B extension that reaches the NOUN)
`activities` is the FOURTH taste dimension and the only one that decides WHICH STOP EXISTS. Shipped 2026-08-08; live-verified against the real model (then on Groq) before the survey question was written.
- **`aesthetic` is an ADJECTIVE, `searchQuery` is a NOUN — that distinction is the whole feature.** style/foods/dietary shade what a stop is LIKE (`style` → `context.aesthetic` → prepended verbatim to every Places query by `buildQuery`). Only `activities[].searchQuery` decides what KIND of stop exists, and code never inspects it — it becomes `category_signals`, then one Places search per entry. A preference that cannot reach that field cannot steer an activity, which is why "just add a survey question" would have collected dead weight.
- **FIVE options, and the shortness is load-bearing**: art / outdoors / games / active / music. Theatre-and-shows, classes/workshops, nightlife, shopping and spa were considered and REJECTED — a theatre or a class is a SHOWTIME product and there are no showtimes here (the `durations.ts` movie-runtime gap), and nightlife fights the VARIETY caps. No "Other": it names no kind, so it could only ever be dropped. Do not add a sixth without proving the planner can steer to it.
- **The phrases are PLACE KINDS, never venue FEATURES, and that is a safety property.** art→"art gallery", outdoors→"park", games→"board game cafe", active→"climbing gym", music→"live music venue". "live music" is provable from `constraintEvidence` and is a genuine thing to ask for; "live music venue" is a kind of place and can never be one — which is exactly what makes the strip below safe to run. A test pins that no activity phrase equals a provable-constraint string.
- **THE CONSTRAINT-LEAK STRIP IS MANDATORY, and it is the swap engine's strip applied to the planner path.** `constraints` is ONE plan-level array applied to EVERY slot (spliced into every query by `buildQuery`, proved from six provider booleans in `selectVenues`), so a leaked activity kind is a permanent whole-plan `unmet_constraint`. `isLeakedActivityConstraint` (plannerPreferences.ts) + `stripLeakedPreferenceConstraints` (planner.ts, applied in the route beside `applyTimeFloors`). **An EQUALITY test on `normalizeConstraint`, never a keyword list and never containment** — "live music" is contained in "live music venue" and is a real request, so anything looser deletes what users actually said. KNOWN RESIDUAL: a leaked VARIANT ("art" for "art gallery") is not caught; the prompt forbids it and a looser rule would cost more than it saves. `strippedConstraints` on `planner_plan` is a COUNT only — the tuning signal, naming nobody's taste.
- **It RESOLVES the vague aspect.** Per the prompt's own resolve rule, an activity preference settles a bare "something to do": `confident: true` and no "what kind of thing?" question. Verified live across all five options. A stated activity still wins outright ("bowling tonight" + an art profile → a bowling alley, nothing else).
- **`style` is now PURE VIBE** (chill/lively/trendy/cozy/adventurous). `cultural` was RETIRED because it was an interest wearing a vibe's clothes and would have steered the same choice twice. Retiring a slug needs no migration: `normalizeAnswerSet` intersects against the closed option set on the way OUT of storage, so an old profile's `cultural` is dropped on read and the rest survives.

## Shipped — optional Google login (Stage 1A, login only)
Firebase Auth, client SDK only (**corrected 2026-08-04: "no `firebase-admin`, no Firestore, no server-side token verification" was true of 1A ONLY — Stage 1B shipped all three, and Stage 2 reads Firestore back; see the history-reader section above**). `app/lib/firebase.ts` (guarded init) → `app/lib/authUser.ts` (pure mapping + label/initials) → `app/lib/useAuth.ts` (hook) → `app/LoginScreen.tsx`, mounted from `app/page.tsx`.
- **GUEST = NO-AUTH = FULL APP.** Nothing is gated on being signed in; in this slice a guest and a signed-in user get identical behaviour, and signing in only CAPTURES a uid for later stages. No route under `app/api/**` knows auth exists.
- **A missing key must never take the app down.** `firebase.ts` does no work at import time and every entry point returns null instead of throwing. It requires ALL SIX `NEXT_PUBLIC_FIREBASE_*` values (blank counts as absent) — a partial config otherwise fails deep in the SDK at popup time with an opaque message. Unconfigured degrades to "sign-in unavailable", never a white screen; the guest path is unaffected. The SSR bail-out happens BEFORE the resolved-cache is set, because caching a server-side null would poison the client.
- **The SDK OBSERVER is the single source of truth** for who is signed in — sign-in never sets user state from the popup's return value, so the login card and the account corner cannot disagree. Every failure path (unconfigured, SDK threw, listener error) lands on `signed-out`, which is a fully working state: the UI must never strand on a spinner waiting for a session that is not coming.
- **The observer is `onIdTokenChanged`, NOT `onAuthStateChanged`, and swapping it back reintroduces a real bug** (fixed 2026-08-09). The auth-state observer notifies only on a UID CHANGE — the SDK gates it on `lastNotifiedUid !== currentUid` (`@firebase/auth` `notifyAuthListeners`) — and `signIn()` upgrades a guest with `linkWithPopup` precisely BECAUSE that keeps the uid. So the single most important transition here, `isAnonymous` true→false, fired no auth-state event: React held a user that still said "guest", `signedInForReal` stayed false, the `/api/profile` read that gates the onboarding survey never ran, and a brand-new account saw no survey until it reloaded. Firebase's own docs point at the token observer for exactly this ("To keep the old behavior, see `onIdTokenChanged`"). The RETURNING-account path was never affected: its link conflict falls to `signInWithCredential`, which mints a different uid.
  - **The price of the superset is paid by `sameAppUserIdentity` (`authUser.ts`), and that guard is mandatory.** `onIdTokenChanged` also fires on every token refresh — hourly, and again on each `getIdToken()` that renews, which is every authenticated request — and `toAppUser` mints a FRESH OBJECT each time. Storing them all would churn `user`'s identity on a timer and re-run every effect keyed on it. The subscription therefore stores a new user only when an observable field moved (uid / isAnonymous / displayName / email / photoURL — every field the UI reads, so nothing can go stale on screen), which makes a pure refresh inert while still delivering the anonymity flip. `setStatus` stays unconditional: React does not re-render on an identical string.
- **The login screen is an ENTRY POINT, not a gate** — reached from a "Sign in" affordance in the hero corner rather than shown on arrival. This is deliberate: every e2e spec does `goto("/")` then fills `.prompt__input`, so an arrival interstitial breaks all 73, and gating it behind a test-only flag would fork product logic under test (which the mock-seam rule forbids). Escape and "Continue as guest" both dismiss; dismissing without signing in IS the guest path.
- Auth UI uses the card/ink/accent language and **must never use `--live`** — see the UI invariants.

## UI invariants (don't regress)
- Acid green (`--live`, `#C8F000`) is reserved — including through the soft-blue re-skin, which changed every other value and left this one alone. It means "happening now / just changed" and nothing else; auth and other chrome must not borrow it. The FULL chartreuse marker/border = the active "now" stop only. Swap-/reroute-changed cards and times may use chartreuse *accents* (changed-ring marker, settling time pill), but ROUTE GEOMETRY IS NEVER RECOLOURED TO IT: authentic transit colours win and a wider, low-opacity same-colour halo carries the changed signal. An upcoming changed stop keeps its ink marker — chartreuse never means "changed" and "now" at the same visual weight. Never decoration.
- Swap vs reroute vs remove: swap is user-initiated + surgical (one upcoming stop, hold the slot); reroute is disruption-driven + replans the tail; remove deletes one stop and closes the gap. All three share `floorTime()` and the SAME `resettleTail` cascade — never fork a fourth replan path.
- **`--danger` (`#A3372F`) is reserved the way `--live` is**, for one meaning: "this ends something, and it cannot be undone". The armed remove state, the End control, and error text. Nothing merely emphatic borrows it, and it never means "changed" or "now".
- Map uses inline `styles` JSON on a classic `Map` (no `mapId`) so paper styling works; markers/cards are `OverlayView` HTML, NOT AdvancedMarkerElement (which needs a Cloud map id).
- fitBounds keys off venue coordinates (`fitKey`), never status ticks — status changes must not yank the map view.
- **A far HOME does not get to decide the frame.** `homeFitsWithStops` folds home into the opening fit only while it stays within `max(stopsRadius, 1_500) × 3` of the stops' centre — a RELATIVE test, because "too far" is a fact about the plan's own size. A flat 40 km ceiling was tried first and a live 35 km Oakville start sailed through it with both downtown stops landing on one dot. Past the threshold the fit is the STOPS; home is still drawn at its real coordinates with its route leading off-frame. Never fake a marker's position to keep it on screen, and never drop the home marker.
- Expanded cards clamp to the viewport (horizontal) and flip below the pin near the top edge.
- Stop summaries are native selection buttons; the inline swap form is their sibling, never nested inside an interactive card. Successful swaps/reroutes move keyboard focus to the changed strip stop after React commits.
- At ≤560 px the three landing fields stack with horizontal separators. Primary controls keep a 44 px target, and interactive map chips remain clamped inside the viewport.
