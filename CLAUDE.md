# CLAUDE.md — Itinerary

Operational rules and invariants. Read this before making changes.

## What this is
Hyperlocal AI day-planner. Free-text prompt → one executable outing (real venues, real times, real transit), rendered on a map, that heals itself when transit breaks. The user supplies the CITY and starting address (Toronto/Ossington is the prefilled default and the pre-multi-city fallback, no longer the only target); each plan carries its own resolved IANA timezone. Next.js, Groq (an ordered per-call-type model chain, `llama-3.3-70b-versatile` first — see the models section), Google Geocoding/Places/Routes/Weather/Maps, and Firebase Auth for OPTIONAL Google sign-in (the app is fully usable with no account).

## Core architecture rule (governs everything)
The LLM does semantic work only: shaping the day, selecting venues, writing reasons. Code does every verifiable fact: hours, prices, ratings, distances, travel times, scheduling. Never let the LLM compute distance/time or check "is it open" — that's a field comparison, not a judgment call. If a change asks the LLM to do something checkable, that's the bug.

The LLM is a PROPOSER, never an authority. Its plan is an input code validates, exactly as `selectVenues()` treats its own output (invalid ids → one retry → deterministic fallback; "a correction is not trusted merely because it parsed"). It proposes intent and estimates; code owns the arithmetic — real travel legs, real opening hours, actual end times, whether the plan genuinely fits the window. If the planner says four activities fit between 3 and 8 and the real legs make it six hours, code catches that: the LLM never gets to be wrong about a number that can be checked.

## Models and the fallback chain (`app/api/_shared/models.ts` + `modelFallback.ts`)
ONE file owns every model id. It replaced three independent `const MODEL` declarations (parse/select/swap) — the reason a model change used to mean editing three files and remembering all three existed. Chains are ORDERED and PER CALL TYPE, env-overridable via `GROQ_MODELS_PLANNER` / `_SELECT` / `_SWAP` with in-code defaults.
- **Why per call type, not one chain.** Groq rate-limits PER MODEL, so a separate swap primary means swap traffic never spends the planner's budget — under the load that causes this problem (re-planning plus repeated swaps) a shared chain would have swaps pushing the planner toward its own limit. Quality confirms the split: `llama-3.1-8b-instant` classifies swap intents correctly (with `parseTimeExpr`/`parseDurationExpr` owning the numbers underneath) but in SELECT it picked a venue with no evidence for a hard constraint — the exact hedge the prompt forbids. Never put the swap primary on the select chain.
- **Only 429 and provider-side 5xx advance the chain** (`ProviderError.isModelRetryable`). A 401/403 is the same key failing identically on every model, so advancing burns the chain and buries the real problem; a 400 is our own malformed request. `readProviderJson` no longer discards the status: `ProviderFailure` carries `upstreamStatus` + `retryAfterSeconds`, and 429 gets its own `*_rate_limited` code. The public message/status stay generic — this is about what the SERVER knows.
- **The fallback wraps ONE LOGICAL CALL**, which for the planner and select includes their own correction retry. A correction is a reply in a conversation; letting it land on a different model than the answer it corrects is a subtler bug than the rate limit it works around. `selectModelCall(apiKey, model)` exists to bind a completion to one model across that ladder.
- **Chain exhaustion is a 503 `model_capacity_exhausted`** with an actionable message and `Retry-After` — never the generic provider text. EXCEPT swap, where exhaustion falls to the deterministic `localFallback()`: that call has real parsers beneath it, so degrading beats refusing. That is a decision, documented at the call site.
- **Never pick a chain model from memory.** Probe `GET https://api.groq.com/openai/v1/models` and run the candidate against the real system prompt in JSON mode. `qwen/qwen3.6-27b` fails Groq's own JSON validation and `groq/compound-mini` is an agentic tool-using system — both were rejected that way. A chain entry that cannot hold the contract is worse than a shorter chain.
- **A weaker fallback is safe because the validation ladders are untouched.** `findPlanProblems`/`findProblems` → correction retry → deterministic fallback catches junk from any model; `gpt-oss-120b` returning `activities: []` on a vague prompt was caught and rescued by exactly that machinery. Do not weaken any of it to accommodate a weaker model — that is what makes this change low-risk. Every attempt is logged (`model_call`, `model_unavailable`, `model_chain_exhausted`): running degraded silently is worse than running degraded.

## The pipeline (in order)
typed city/address geocode → LLM PLANNER → [clarifying questions, one round] → weather fetch → Places search (one per activity; bounded late-night expansion) → objective filter → LLM select (+ duration refinement) → travel (computeRoutes) → schedule + window validation → map. Each step is its own module and was built/tested in isolation.

**The geocode runs FIRST** (reordered 2026-07-27): the planner resolves "tonight"/"in an hour" against a real clock, so it has to be told WHICH clock, and only the geocode knows the plan's zone.

## The planner (`app/api/parse/planner.ts` + `app/api/parse/route.ts`)
`/api/parse` is a PLANNER, not an extractor. It is sent the prompt, the city, — the key enabler — the current instant in the plan's timezone with the weekday named, and (Stage 3B, only for a verified non-anonymous caller with a stored profile) a `preferences` object. It returns `{ activities, timeIntent, questions, context }`: which activities make the day, what to search for per activity, a duration estimate per activity, a resolved start/end, and up to three clarifying questions. `planToParsed()` projects that onto `ParsedPrompt`, so Places/filter/select/swap/reroute/the store all keep working unchanged.
- **`time_window` is PROSE now.** On the planner path it is a display label only; the resolved instant travels explicitly (`targetTime` into the search route, `startOverride` into `buildSchedule`) so search, the hours filter, the weather gate and the schedule all share ONE anchor. `resolveStartTime`'s category defaults survive as the fallback for callers that don't come through the planner (swap, reroute, legacy stored plans).
- **`stop_count` is always null** on the planner path: the activity list IS the count.
- **Validation is non-negotiable** and mirrors `selectVenues`: `findPlanProblems()` → one correction retry with the problems spelled out → a deterministic fallback (one general activity at the next full hour + the broad questions). A raw model error never reaches the user. Durations are CLAMPED (15–360) rather than rejected — arithmetic code can fix does not deserve the one retry, and the same bargain covers a window the user is already INSIDE: `windowUnderway()` clamps a past start up to `now` and keeps the stated end, because "5-9pm" asked at 6:30 is a real still-open window, not the mis-resolved date `MAX_START_LAG_MINUTES` catches. That repair is narrow on purpose — a past start with NO end, a fully passed window, and a sliver too short for the shortest stop all still fail. `planner.test.ts` is heavily covered (35 cases) and must stay that way — every rule above is load-bearing. (It is not the largest suite: `swap.test.ts` has 79 cases and `schedule.test.ts` 43 — verified 2026-08-08.)
- **Code-owned guarantees the model cannot skip:** an unspecified time always ships a when-question; questions are capped at 3 (vague-attached first, then when); slots are renumbered dense; question ids are made unique; the immediacy, all-day and WEEKDAY floors read the RAW prompt and override the model. The weekday floor exists because live runs had "plan my saturday" landing on Friday: which date a named weekday falls on is a fact, so code re-derives it and shifts the window as a unit, keeping the stated wall-clock hours. It corrects facts, not readings — it abstains on a competing calendar phrase and leaves a correct resolution alone.
- **A stated range rolls as ONE unit.** Both ends belong to the same day, decided by the END (a window whose end has passed is tomorrow's; one underway is still today's). Rolling each end independently produces an inverted window that the validator rejects, silently downgrading a good prompt to the fallback — and it is invisible to any test with a fixed `NOW`, which is why `fixtures.test.ts` sweeps all 24 hours.
- **Durations: the LLM estimates, code bounds.** The planner proposes `estimatedMinutes` per activity; `selectVenues` REFINES it against the venue actually picked (folded into the existing Groq round-trip via a `minutes` field, not a second call — an extra round-trip per plan is real latency). Both are clamped to 15–360; the resolved value rides ON the selection as `plannedMinutes`, like `priceLevel`/`description`/`currentOpeningHours`, so nothing downstream re-derives it. `buildSchedule` prefers the stop's own duration and falls back to `DURATION_TABLE` — which must NOT be deleted: swap, reroute and recovery slots create stops without a planner pass, exactly like `home.ts`'s `HOME` constant. Only the BASE is the model's to judge; the buffer stays the table's scheduling margin.
- **Window validation (code owns the arithmetic).** When the planner states an `endISO`, `checkWindowFit()` re-checks the plan against it AFTER real travel legs are folded in — the concrete case the architecture rule names. Inside `WINDOW_OVERRUN_TOLERANCE_MINUTES` (30) nothing happens: a stated window is rough intent, and dropping a whole activity to recover fifteen minutes is the worse harm. Past that, the trailing stops that don't fit are dropped and NAMED in the banner (`windowOverrunMessage`); if not even the first fits, it fails loud (`windowTooTightReason`). A large unfilled gap is the planner under-filling — logged as `[window-fit]`, never filled in code, which would be a second planning mechanism in the wrong language.
- **Questions are LLM-authored, one round.** Answers go back for a SECOND planner pass rather than being merged client-side — folding free-form answers onto searchQueries and a time intent is the same judgment the planner just made, and doing it twice in two languages is how the old rule table grew. Skipping always still plans.

## Non-negotiable invariants
- **Reroute floor_time:** floor_time = max(now, active stop's end). Stops at or before floor_time NEVER change. Locked stops never change. If any change violates this, STOP and flag it — do not paper over it.
- **Reroute blast radius + anchor:** a reroute replans ONLY stops strictly downstream of the disrupted leg (timed positions ≥ legIndex+1); stops upstream of the break keep their COMMITTED times even when the outing hasn't started. The replanned chain departs at max(floor, previous kept stop's committed end) — never re-derive the schedule from `now`; the clock only wins once it has overtaken the plan. `anchor_time` (that departure instant) is what the banner shows; `floor_time` stays the guarantee value. The `[reroute-apply]` log prints committed starts, floor, affected set, and post-reroute starts — check it first when a reroute moves the wrong stops.
- **Locked ratchet:** a stop locks when active or past, and never unlocks — survives completion and backwards time travel.
- **Keep-on-missing-data:** never drop a venue for missing data (no price, no hours, no rating = keep). Applies to every filter rule. ONE exception, and it is not a filter rule: a PRICE-DIRECTION swap ("fancier"/"cheaper") never hands back an unpriced venue AS its result — see the swap section. The rule forbids DROPPING a venue for a missing field; it does not require answering a price question with a venue that has no price. Ordinary swaps and every filter still see those venues untouched.
- **ID validation on select:** the LLM picks by venue ID only; invalid ID → one retry with correction → highest-rated fallback flagged. It can never invent a venue.

## Reuse, don't fork
The replan reuses the real pipeline via `searchPlaces.ts` and `selectVenues.ts` (callable cores; the routes are thin wrappers). Reroute imports these — never fork a parallel replan path, or fixes drift.

## Standing policies
- API keys server-side in `.env`, one per Google service, restricted in Cloud Console. Two things are deliberately browser-side (`NEXT_PUBLIC_`): the Maps JS key, protected by referrer restriction, and the six `NEXT_PUBLIC_FIREBASE_*` values, which are client config by design rather than secrets (Firebase enforces access through Auth rules and authorized domains, not key secrecy). Everything else stays server-only — the Geocoding key in particular has its own `GOOGLE_GEOCODING_API_KEY`.
- Unstated times resolve via CATEGORY_START_DEFAULTS (dinner 19:00, brunch 10:30, etc.) before falling to next-full-hour. Past times roll forward to next day. This is the fallback for callers that do NOT come through the planner (swap, reroute, legacy stored plans); the planner's own resolved start wins outright when present.
- One resolved `startInstant` is shared by scheduling, hours filtering, and the weather gate — they must never diverge.
- **Per-plan timezone (zone-aware everywhere):** every plan carries one resolved IANA zone (`itinerary.timeZone`, from `zoneFromLatLng` on the geocoded start; default `America/Toronto`). ALL scheduling math ("now"/"today"/which-hour), the hours filter's day-of-week + hour, and every display label render in THAT zone — never the server's wall clock, never the viewer's browser, never unconditionally Toronto. Zone math lives ONLY in `app/lib/zoneTime.ts` (luxon + tz-lookup, both offline); do not hand-roll `Intl.DateTimeFormat` parsing — that caused prior TZ/meridiem bugs. `toZonedISO(d, zone)` is byte-identical to the old Toronto formatter for the default zone, so Toronto plans are unchanged. When threading a new time computation, pass the plan's zone (`itinerary.timeZone ?? DEFAULT_ZONE`); `wallClockParts().weekday` is 0=Sun (NOT the day-of-month `day`). Note: `TZ=America/Toronto` on the server no longer drives scheduling (it's per-plan now) and `new Date()` is an absolute instant, so the server's zone is irrelevant to scheduling. **The `usableByHours` exception previously recorded here is RESOLVED** (corrected 2026-07-31): the swap engine's default availability check now judges the instant on the venue's local clock via the shared `isOpenAtInstant`, takes a `timeZone` parameter, and both call sites (`swap.ts:705`, `swap.ts:1577`) pass the plan's zone. No production path reads `getDay()/getHours()` any more — the only remaining occurrence is the comment in `swap.ts` describing the old behaviour, plus `MOCK_RAIN_HOUR` in the mock fixtures, which is test data. FLAGGED, not resolved: DEPLOY.md still requires `TZ=America/Toronto`, and this was its stated justification. Re-evaluate that requirement on its own evidence before dropping it — this reconciliation did not audit DEPLOY.md's other reasons.
- Transit legs get a +5 min delay margin; that buffer is separate from stop-duration buffers. A leg relabels as walk (no margin) when it's short (<400m), or when walking beats transit+margin AND the walk is ≤30 min (`MAX_WALK_LABEL_MIN`), or when walking is at least twice as fast as transit (broken-transit escape hatch, any length) — a 75-minute walk must never be presented over a similar transit ride. A hop below the stricter 250 m haversine threshold skips TRANSIT upstream and requests WALK only. If both modes fail, the fallback stays `unknown`, uses a 1.35× detour allowance plus 20% uncertainty (minimum 5 min), and draws no map route. Every displayed WALK route carries the provider-required visible/accessibility caution.
- **Location (multi-city):** the CITY and STARTING ADDRESS are plain text inputs on the empty state — resolved by the purpose-built Geocoding API via `POST /api/geocode` and its dedicated server-only `GOOGLE_GEOCODING_API_KEY`. City results must be locality-typed; addresses are biased to and objectively checked against the resolved locality/administrative region/country. Multiple valid matches enter `recovery.mode: "geocode"` for an explicit formatted-address choice; never take provider index zero. The chosen formatted city rides on `parsed.city` (app-injected, never LLM-inferred) so Places/swap/reroute searches stay disambiguated; the chosen start is stored as `itinerary.home` and everything home-related reads `itinerary.home ?? HOME` (the Chestnut default exists ONLY for pre-multi-city itineraries and tests). Weather takes `?lat=&lng=`. The parse's `location` field is a neighbourhood WITHIN the city, never a city. Never silently fall back to Ossington/Toronto for a user-entered city. Real location services / geolocation remain deliberately unbuilt — plain queries only.
- **Places call/cost boundary:** the complete Text Search mask is intentional: identity/location, business status, hours, rating, price, stop-card description, and provider-structured constraint evidence all have deterministic consumers before selection. Named categories cost one call (two late-night variants at most), the general pool five, and eight categories cap an attempt at 16 calls. Identical query+type work deduplicates only inside one attempt. Never cache full Places content across attempts (provider-policy and hours-freshness boundary); place IDs are the long-lived identifier. A discovery→Details split is not a cheaper fact-safe shortlist under the current field/pricing shape.
- **Persistence seam:** routes access the itinerary store ONLY via `loadItinerary`/`saveItinerary` (store.ts). KV env vars set → Upstash Redis REST is the source of truth (always read Redis, always write back after mutations — `withStatuses`' lock ratchet mutates even on GETs and refusals); unset → the in-memory Map (dev/e2e). Engines never touch the store. Serverless without KV fails loud. Deployment (env table, Maps-key referrer restriction, TZ=America/Toronto requirement) lives in `DEPLOY.md`.

## Fail-loud surface (operational notes)
`app/lib/planGuards.ts` is THE surface for bad input — every degenerate/impossible/contradictory prompt must land there (or in `resolveStartTimeChecked`'s malformed-input messages) with a reason + suggested fix; an empty map or a borrowed error from another branch is the bug. Guard order in `runPipeline`: degenerate prompt (pre-Groq) → unparseable parse → contradiction → [clarify questions] → malformed time input → all-pools-empty net → unmet constraint → PARTIAL-failure recovery (the interactive panel below). **There is no plausibility gate** (removed 2026-07-27): an unusual hour is planned, and the objective hours filter decides what is genuinely open — "nothing's open at 3am" is a fact, "brunch isn't plausible at 3am" was an opinion. A hard refusal string is the right answer only when there's no real choice to offer; once there IS one (a weather block, a partly-empty plan), it belongs in the recovery panel instead — see the next section. Constraints are enforced in `selectVenues`: no evidenced candidate → `id:null + unmet_constraint` (valid, no fallback), and a code-side hedge guard converts "worth confirming / may accommodate" picks into the same failure — never suggest a venue while telling the user to verify a constraint. `priceLevel` + `description` ride ON the stop (Selection → SelectionLike → ItineraryStop, set by swap's buildStop/finalize too); the strip must read the stop's own fields before any pools lookup, which goes stale after swaps.

## Shipped — interactive recovery panel (operational notes)
ONE component in `app/page.tsx` (`recovery` state, a discriminated union on `mode`), three triggers (a fourth, `time-gate`, was removed with the plausibility gate on 2026-07-27). Never build a parallel panel for another case — add a mode.
- **`mode: "geocode"`** — the purpose-built geocoder returned more than one valid typed city or in-city address. Show the formatted-address candidates and resume with exactly the chosen candidate; do not repeat the ambiguous request or select index zero.
- **`mode: "empty"`** — partial failure: some categories picked, ≥1 pool came back empty. `partialEmptyCategories` detects it (all-empty stays on `noVenuesReason`, never routes here). Each row shows `emptyCategoryReason` (the honest dominant reason from the objective drop log) + a widen offer (re-search city-wide via `categoriesOverride`, suppressed per-row by `noWiden`) + a free-text replace + "Plan without it" (shown only when some other stop actually resolved).
- **`mode: "weather-gate"`** — a category was emptied by the weather gate specifically, while others survived. "Still want it" re-searches that category with `weather: null`, which skips ONLY the weather gate via keep-on-missing — hours/rating/price/business status all still run, and no server change was needed. Resolved categories must be cleared from `weatherBlocks` (a planned stop is not "skipped"). Still-empty falls into `mode: "empty"`, never a third dead end. "Something else" scopes to the SLOT (replace rows with `noWiden`), not the whole-plan kind picker — other stops survived and discarding them would be wrong. The ALL-weather-blocked path keeps `weatherBlockedReason` untouched.
- Shared plumbing: `searchSlot` (one category search+select, with `dropLocation`/`ignoreWeather` switches) and `mergeSlot` — widen, replace, and both overrides go through the same fetch path. `orderByRequest` restores prompt order afterwards, because `selectVenues` appends empty categories LAST and recovery resolves them in that appended position.

## Shipped — swap engine (operational notes)
Per-stop swap (`app/api/itinerary/swap.ts`, `POST /api/itinerary/[id]/swap`): user taps an UPCOMING stop, types a complaint, the engine acts on intent — VENUE (replace, hold slot), TIME (move the slot), DURATION (change how long), or CONSTRAINT (re-search). Distinct from reroute (external disruption → downstream replan). `floorTime()` shared from `store.ts` by both engines.
- **Time / duration swaps**: `parseTimeExpr` (relative "an hour earlier" = -60, absolute "after 8" = 20:00, meridiem anywhere "6pm" = 18:00, bare "3:30" = 15:30 — assume PM only for meridiem-less times; a number owned by a duration unit, "make it 2 hours", is never a clock time) and `parseDurationExpr` (absolute "stay 2 hours" = 120, relative "stay longer" = +30) are the deterministic floors under the Groq interpret — arithmetic never depends on the model. Merge rules: a locally-parsed ABSOLUTE time always beats the model's; an EXACT local relative beats the model's; only a VAGUE local relative ("a bit earlier") accepts model refinement, and only same-sign ≤3h — garbage deltas must never drift a stop across the day. A phrase with BOTH halves ("start at 6pm for 2 hours") routes to time and applies the duration alongside via the shared `resolveNewTotal` bounds — neither half is ever dropped. A time-swap moves the slot, never resizes it, and a VENUE swap holds the whole slot, length included: the stop's customized `durationMinutes.total` is the source of truth everywhere a swap keeps the same category. It resets to the (new) category default only when the stop changes KIND — a category-changing research swap, or an engine-adapted replacement venue. The `[swap-apply]` log in `swapStop` prints intent + before/after start/total — check it first when a swap changes the wrong field. Both call the reusable **try → adapt → notify** ladder `resettleTail` (shift/reflow the tail, keep a downstream venue if still open at its new arrival, else re-search an equivalent, else fail loud). Plan-then-commit: a failed resettle leaves the itinerary untouched. Duration guards: floor at the category's realistic minimum, cap 6h. `buildStop` takes a `durationOverride`; `resettleTail`/`commitTail` carry each stop's `totalMinutes` so a custom duration survives a later reflow. Keep `resettleTail` generic — it's the shared spine of time + duration (and future) swaps.
- **Price-direction swaps ("fancier"/"cheaper") rank in CODE, or refuse.** `parsePriceDirection` reads the RAW refinement (never `interp.budget`, which is the model's echo) and `rankByPriceDirection` keeps only candidates STRICTLY past the current stop's own `priceLevel` — the same shape as the `CLOSER_PATTERN` distance block, for the same reason. Same-tier is not a move: allowing it is what made repeated "fancier" swaps ping-pong A→B→A. `ranked` is the WHOLE eligible set. An unpriced venue is reported but never presented as the answer (the keep-on-missing exception above): it cannot be shown to move in the requested direction, and the earlier `ranked.length > 0 ? ranked : unpriced` fallback is exactly how a park or attraction — a category Places prices for nobody — returned an arbitrary venue as "fancier". Two refusals, and the difference is a fact not a tone: `comparable` false (NO candidate priced) can only say "can't compare prices", because "it's already the priciest" is a claim about data nothing here has. Best effort survives in one place only — no price on the CURRENT stop while candidates ARE priced ranks them most-extreme-first rather than refusing. Price words are also stripped from `constraints` at all three producers (localFallback / judge / search): `buildQuery` splices constraints into the Places query verbatim and `constraintEvidence` proves them from six provider booleans, so a leaked "nicer" is both query noise and a permanent unmet_constraint refusal.
- **Category-CHANGING swaps ("board games instead") ride the existing venue/constraint intents — no new intent, no client-contract change.** The model's `category` is its ANSWER and `path` is only its classification, so ONE effective `path` is derived once (`interp.path === "research" || changesCategory`) and drives the pool, the search parse AND the path reported back — deriving it per consumer is how a swap searches a new kind through the refilter parse and then tells the client it narrowed the old pool. The stop takes the NEW kind's default length (honest length, not the old slot's — `finalize` already did this); `resettleTail` absorbs it downstream, and a length that strands a locked stop REFUSES with the collision named. (Pushing later stops back to make room SHIPPED on 2026-08-08 — see the slot-push section below. It applies to the INBOUND-unreachable case; a length that strands a LOCKED stop still refuses, because a locked stop is never movable.) **The category is stripped from `constraints` at the same place price words are**, and for the identical reason: a KIND of place is unprovable from `constraintEvidence`'s six booleans, so a leaked one makes `placeMeetsAllConstraints` false for every venue that exists — a permanent unmet_constraint refusal. The strip is an EQUALITY test against the new category (via the judge's own `normalizeConstraint`), deliberately NOT a keyword list: "patio" is a genuine provable constraint and any list broad enough to catch "board games" would eat it. Refusals name the REQUESTED kind, with the right article ("a board game cafe" vs "another bar"). The same-category guardrail for "something different"/"surprise me"/"somewhere else" lives ONLY in `REFINE_SYSTEM` and is pinned twice — an engine case (a same-category interpretation must stay on `refilter`) and a case asserting the prompt still names those phrases. Neither pins the live model; a live probe of the tuned prompt classified 10/10 correctly (2026-08-07).
- **Availability seam**: `SwapDeps.isUsableAt(place, when, category)` is the ONE "is this venue usable then" check (default = objective hours, keep-on-missing). A real availability/reservation API replaces that function body only. It is asked TWICE — at arrival and at the last moment actually spent at the venue — so a venue that closes MID-SLOT is no longer a legal answer (a coffee shop closing at 9:30 used to fill a 9:00–10:00 slot, because `isOpenAt` is a single-instant check and every caller passed the start). Two boundaries are deliberate and load-bearing: the far end is OCCUPANCY (`total` minus the table's buffer — the buffer is scheduling margin, and judging against it adapted a bar closing at 22:00 away from a 20:55–21:55 stop), and it lands one minute inside the end, because occupancy is [start, end) and `isOpenAt` reads the closing minute as closed. `usableForProposal`'s `slotMinutes` is REQUIRED so no new call site can silently keep arrival-only; pass `ARRIVAL_ONLY` explicitly for a downstream stop this swap does NOT move — the initial pipeline's `filterPools` is still arrival-only, so re-judging an untouched stop here lets an unrelated swap silently re-kind stops the user never touched. **FOLLOW-UP, not done:** that planner-side asymmetry belongs in `filterPools`, not in a swap.
- **The SLOT PUSH — a replacement too far to reach moves its own slot later, and the tail with it.** `finalize`'s `startISO` is the slot's REQUESTED start, never a guarantee. `planAnchorInbound` no longer collapses "can't get there by then" into the same `null` as its six genuinely-unverifiable cases; it returns `earliestStartMs` (previous stop's committed end + the REAL leg) as a FACT and each caller sets policy. `finalize` takes `Math.max(requested, earliest)` — that one operator IS the never-earlier guarantee, and a reachable start leaves the slot byte-identical to the old path — then runs the UNCHANGED `resettleTail`, which already owned the cascade. **The route is planned BEFORE the usability check now**, because "open for the whole slot" cannot be answered until the slot is resolved.
  - **TIME and DURATION swaps still REFUSE** (`reachesStart`). A time swap NAMED that time; landing the user at 8:20 because 8:00 was unreachable answers a different question. A duration swap is not moving the start at all.
  - **The FIRST timed stop never pushes**: with no previous stop `earliestStartMs` IS the requested start, because the origin is home and a home departure is not a committed boundary. Today's behaviour, unchanged and now explicit.
  - **HARD limits are inherited, not re-implemented** — that is the whole design. Closing time (`usableForProposal`, incl. the open-at-END check, which every pushed stop gets because `movedByThisSwap` is true for it), locked/past stops, and real-leg recomputation all live in `resettleTail` and were not touched. A stranded stop REFUSES and NEVER prompts: consent cannot open a closed door. The refusal keeps `resettleTail`'s own message (which names the stop and the instant) and prefixes the push context.
  - **The SOFT limit is the one net-new constraint: `itinerary.plannedEndISO`.** Nothing enforced the user's stated end after a swap before — `checkWindowFit` runs once, in `page.tsx`, against a planner result the browser was still holding. The instant is now persisted at creation (`storeItinerary` → `parseOptionalInstant` → `createItinerary`), because it outlives the request that knew it. **ABSENT MEANS NO CEILING** — most plans, every pre-2026-08-08 plan — and the push then runs as late as real hours allow. Code must never invent one.
  - **Past the stated end it ASKS, it does not refuse.** `SwapResult` gains an optional `confirm: EndTimeConfirm` on the `swapped: false` arm — present ⇒ a QUESTION, absent ⇒ a refusal. `swapped` stays false, so the route reports `changed: false`, no CAS runs, and declining is free by construction. Accept re-sends `endTimeAccepted: true`, which skips ONLY that guard and re-runs the swap from scratch (no cached proposal — the engine holds no per-request state; `version` still rides along, so a plan that moved underneath 409s). The tolerance is the SHARED `WINDOW_OVERRUN_TOLERANCE_MINUTES` (30), deliberately not a second number: two definitions of "past the stated window" is how creation silently accepts 25 minutes while a swap interrupts over five.
  - **The "5 attempts" in `resettleTail` is RETRIES-PER-STOP, not cascade depth** (verified 2026-08-08) — it iterates `findReplacement` candidates for ONE stop. The cascade is `for (k = anchorPos + 1; k < timedIdx.length; k++)`: the whole tail, unbounded, terminating at a locked stop or the end of the list. There was no artificial ceiling to raise.
  - **UI**: `SwapEndTimeDialog.tsx`, mounted from `page.tsx` beside `StopItineraryDialog` and reusing its `.stopdlg` language. Decline is the safe default at every level (escape, initial focus, and nothing written server-side). `doSwap(endTimeAccepted)` re-runs the same refinement. The pushed stop now gets its OWN strike-through, read by INDEX rather than out of `oldById` — that map is keyed by venue id and the venue is exactly what changed.

- **The phrases are PLACE KINDS, never venue FEATURES, and that is a safety property.** art→"art gallery", outdoors→"park", games→"board game cafe", active→"climbing gym", music→"live music venue". "live music" is provable from `constraintEvidence` and is a genuine thing to ask for; "live music venue" is a kind of place and can never be one — which is exactly what makes the strip below safe to run. A test pins that no activity phrase equals a provable-constraint string.
- **THE CONSTRAINT-LEAK STRIP IS MANDATORY, and it is the swap engine's strip applied to the planner path.** `constraints` is ONE plan-level array applied to EVERY slot (spliced into every query by `buildQuery`, proved from six provider booleans in `selectVenues`), so a leaked activity kind is a permanent whole-plan `unmet_constraint`. `isLeakedActivityConstraint` (plannerPreferences.ts) + `stripLeakedPreferenceConstraints` (planner.ts, applied in the route beside `applyTimeFloors`). **An EQUALITY test on `normalizeConstraint`, never a keyword list and never containment** — "live music" is contained in "live music venue" and is a real request, so anything looser deletes what users actually said. KNOWN RESIDUAL: a leaked VARIANT ("art" for "art gallery") is not caught; the prompt forbids it and a looser rule would cost more than it saves. `strippedConstraints` on `planner_plan` is a COUNT only — the tuning signal, naming nobody's taste.
- **It RESOLVES the vague aspect.** Per the prompt's own resolve rule, an activity preference settles a bare "something to do": `confident: true` and no "what kind of thing?" question. Verified live across all five options. A stated activity still wins outright ("bowling tonight" + an art profile → a bowling alley, nothing else).
- **`style` is now PURE VIBE** (chill/lively/trendy/cozy/adventurous). `cultural` was RETIRED because it was an interest wearing a vibe's clothes and would have steered the same choice twice. Retiring a slug needs no migration: `normalizeAnswerSet` intersects against the closed option set on the way OUT of storage, so an old profile's `cultural` is dropped on read and the rest survives.

## Shipped — optional Google login (Stage 1A, login only)
Firebase Auth, client SDK only (**corrected 2026-08-04: "no `firebase-admin`, no Firestore, no server-side token verification" was true of 1A ONLY — Stage 1B shipped all three, and Stage 2 reads Firestore back; see the history-reader section above**). `app/lib/firebase.ts` (guarded init) → `app/lib/authUser.ts` (pure mapping + label/initials) → `app/lib/useAuth.ts` (hook) → `app/LoginScreen.tsx`, mounted from `app/page.tsx`.
- **GUEST = NO-AUTH = FULL APP.** Nothing is gated on being signed in; in this slice a guest and a signed-in user get identical behaviour, and signing in only CAPTURES a uid for later stages. No route under `app/api/**` knows auth exists.
- **A missing key must never take the app down.** `firebase.ts` does no work at import time and every entry point returns null instead of throwing. It requires ALL SIX `NEXT_PUBLIC_FIREBASE_*` values (blank counts as absent) — a partial config otherwise fails deep in the SDK at popup time with an opaque message. Unconfigured degrades to "sign-in unavailable", never a white screen; the guest path is unaffected. The SSR bail-out happens BEFORE the resolved-cache is set, because caching a server-side null would poison the client.
- **The SDK OBSERVER is the single source of truth** for who is signed in — sign-in never sets user state from the popup's return value, so the login card and the account corner cannot disagree. Every failure path (unconfigured, SDK threw, listener error) lands on `signed-out`, which is a fully working state: the UI must never strand on a spinner waiting for a session that is not coming.
- **The observer is `onIdTokenChanged`, NOT `onAuthStateChanged`, and swapping it back reintroduces a real bug** (fixed 2026-08-09). The auth-state observer notifies only on a UID CHANGE — the SDK gates it on `lastNotifiedUid !== currentUid` (`@firebase/auth` `notifyAuthListeners`) — and `signIn()` upgrades a guest with `linkWithPopup` precisely BECAUSE that keeps the uid. So the single most important transition here, `isAnonymous` true→false, fired no auth-state event: React held a user that still said "guest", `signedInForReal` stayed false, the `/api/profile` read that gates the onboarding survey never ran, and a brand-new account saw no survey until it reloaded. Firebase's own docs point at the token observer for exactly this ("To keep the old behavior, see `onIdTokenChanged`"). The RETURNING-account path was never affected: its link conflict falls to `signInWithCredential`, which mints a different uid.
  - **The price of the superset is paid by `sameAppUserIdentity` (`authUser.ts`), and that guard is mandatory.** `onIdTokenChanged` also fires on every token refresh — hourly, and again on each `getIdToken()` that renews, which is every authenticated request — and `toAppUser` mints a FRESH OBJECT each time. Storing them all would churn `user`'s identity on a timer and re-run every effect keyed on it. The subscription therefore stores a new user only when an observable field moved (uid / isAnonymous / displayName / email / photoURL — every field the UI reads, so nothing can go stale on screen), which makes a pure refresh inert while still delivering the anonymity flip. `setStatus` stays unconditional: React does not re-render on an identical string.
- **The login screen is an ENTRY POINT, not a gate** — reached from a "Sign in" affordance in the hero corner rather than shown on arrival. This is deliberate: every e2e spec does `goto("/")` then fills `.prompt__input`, so an arrival interstitial breaks all 73, and gating it behind a test-only flag would fork product logic under test (which the mock-seam rule forbids). Escape and "Continue as guest" both dismiss; dismissing without signing in IS the guest path.
- Auth UI uses the card/ink/accent language and **must never use `--live`** — see the UI invariants.

## UI invariants (don't regress)
- Acid green (`--live`, `#C8F000`) is reserved — including through the soft-blue re-skin, which changed every other value and left this one alone. It means "happening now / just changed" and nothing else; auth and other chrome must not borrow it. The FULL chartreuse marker/border = the active "now" stop only. Swap-/reroute-changed elements get chartreuse *accents* (changed-ring marker, settling time pill, redrawn route) but an upcoming changed stop keeps its ink marker — chartreuse never means "changed" and "now" at the same visual weight. Never decoration.
- Swap vs reroute: swap is user-initiated + surgical (one upcoming stop, hold the slot); reroute is disruption-driven + replans the tail. Both share `floorTime()` and reuse the same pipeline cores — never fork a third replan path.
- Map uses inline `styles` JSON on a classic `Map` (no `mapId`) so paper styling works; markers/cards are `OverlayView` HTML, NOT AdvancedMarkerElement (which needs a Cloud map id).
- fitBounds keys off venue coordinates (`fitKey`), never status ticks — status changes must not yank the map view.
- Expanded cards clamp to the viewport (horizontal) and flip below the pin near the top edge.
- Stop summaries are native selection buttons; the inline swap form is their sibling, never nested inside an interactive card. Successful swaps/reroutes move keyboard focus to the changed strip stop after React commits.
- At ≤560 px the three landing fields stack with horizontal separators. Primary controls keep a 44 px target, and interactive map chips remain clamped inside the viewport.
