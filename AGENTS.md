Operational rules and invariants. Read this before making changes.

## What this is
Hyperlocal AI day-planner. Free-text prompt → one executable outing (real venues, real times, real transit), rendered on a map, that heals itself when transit breaks. The user supplies the CITY and starting address (Toronto/Ossington is the prefilled default and the pre-multi-city fallback, no longer the only target); each plan carries its own resolved IANA timezone. Next.js, OpenRouter (an ordered per-call-type model chain, `meta-llama/llama-3.3-70b-instruct` first — migrated off Groq 2026-08-15, transport only), Google Geocoding/Places/Routes/Weather/Maps, and Firebase Auth for OPTIONAL Google sign-in (the app is fully usable with no account).

## Core architecture rule (governs everything)
The LLM does semantic work only: shaping the day, selecting venues, writing reasons. Code does every verifiable fact: hours, prices, ratings, distances, travel times, scheduling. Never let the LLM compute distance/time or check "is it open" — that's a field comparison, not a judgment call. If a change asks the LLM to do something checkable, that's the bug. The LLM is a PROPOSER, never an authority: its plan is an input code validates.

## The pipeline (in order)
**Corrected 2026-07-31 — this previously described the pre-planner, parse-first pipeline.** typed city/address geocode → LLM PLANNER → [clarifying questions, one round] → weather fetch → Places search (one per activity) → objective filter → LLM select (+ duration refinement) → travel (computeRoutes) → schedule + window validation → map. Each step is its own module and was built/tested in isolation. **The geocode runs FIRST**: the planner resolves "tonight" against a real clock, so it must be told WHICH clock, and only the geocode knows the plan's zone. `/api/parse` is a PLANNER, not an extractor — see `CLAUDE.md` for the full contract and its validation ladder.

## Non-negotiable invariants
- **Reroute floor_time:** floor_time = max(now, active stop's end). Stops at or before floor_time NEVER change. Locked stops never change. If any change violates this, STOP and flag it — do not paper over it.
- **Reroute blast radius + anchor:** a reroute replans ONLY stops strictly downstream of the disrupted leg (timed positions ≥ legIndex+1); stops upstream of the break keep their COMMITTED times even when the outing hasn't started. The replanned chain departs at max(floor, previous kept stop's committed end) — never re-derive the schedule from `now`; the clock only wins once it has overtaken the plan. `anchor_time` (that departure instant) is what the banner shows; `floor_time` stays the guarantee value. The `[reroute-apply]` log prints committed starts, floor, affected set, and post-reroute starts — check it first when a reroute moves the wrong stops.
- **Locked ratchet:** a stop locks when active or past, and never unlocks — survives completion and backwards time travel.
- **Keep-on-missing-data:** never drop a venue for missing data (no price, no hours, no rating = keep). Applies to every filter rule. ONE exception, and it is not a filter rule: a PRICE-DIRECTION swap ("fancier"/"cheaper") refuses rather than hand back an unpriced venue as its result — the rule forbids dropping a venue for a missing field, not answering a price question honestly. Full statement in `CLAUDE.md` (swap engine section).
- **ID validation on select:** the LLM picks by venue ID only; invalid ID → one retry with correction → highest-rated fallback flagged. It can never invent a venue.
- **Context-focused complete travel-leg visibility (2026-08-20):** one exact-ID decision governs every surface of a complete modern leg. Automatic priority is any underway identified WALK/TRANSIT leg, then identified home→first TRANSIT while `displayNow < firstStopStart` (visible from plan creation, including before departure), then the active stop's identified WALK/TRANSIT outbound leg. One ephemeral manual ID may add an identified inter-stop WALK/TRANSIT leg; exact-ID deduplication, retention and clearing remain independent of venue selection. At the exact first-stop start the home exception ends. Home WALK keeps its always-visible, non-manual compatibility behavior; identity-absent WALK and legacy transit behavior remain unchanged and IDs are never inferred. Hidden legs are rejected before geometry decoding or construction, including their whole-leg walks, rides, embedded walks, halos, labels/bubbles and transfer markers.

## Reuse, don't fork
The replan reuses the real pipeline via `searchPlaces.ts` and `selectVenues.ts` (callable cores; the routes are thin wrappers). Reroute imports these — never fork a parallel replan path, or fixes drift.

## Standing policies
- API keys server-side in `.env`, one per Google service, restricted in Cloud Console. Browser-side (`NEXT_PUBLIC_`) is the Maps JS key, protected by referrer restriction, plus the six `NEXT_PUBLIC_FIREBASE_*` values (client config by design, not secrets). Corrected 2026-07-31 — this used to say the Maps key was the only one.
- Unstated times resolve via CATEGORY_START_DEFAULTS (dinner 19:00, brunch 10:30, etc.) before falling to next-full-hour. Past times roll forward to next day.
- One resolved `startInstant` is shared by scheduling, hours filtering, and the weather gate — they must never diverge.
- **Per-plan timezone (zone-aware everywhere):** every plan carries one resolved IANA zone (`itinerary.timeZone`, from `zoneFromLatLng` on the geocoded start; default `America/Toronto`). ALL scheduling math ("now"/"today"/which-hour), the hours filter's day-of-week + hour, and every display label render in THAT zone — never the server's wall clock, never the viewer's browser, never unconditionally Toronto. Zone arithmetic lives only in client-safe `app/lib/zoneTime.ts` (luxon); offline coordinate-to-zone lookup lives in server-only `app/api/geocode/zoneLookup.ts` (tz-lookup), split out to keep its geographic database out of the client bundle (audit B1, 2026-08-31); do not hand-roll `Intl.DateTimeFormat` parsing — that caused prior TZ/meridiem bugs. `toZonedISO(d, zone)` is byte-identical to the old Toronto formatter for the default zone, so Toronto plans are unchanged. When threading a new time computation, pass the plan's zone (`itinerary.timeZone ?? DEFAULT_ZONE`); `wallClockParts().weekday` is 0=Sun (NOT the day-of-month `day`). Note: `TZ=America/Toronto` on the server no longer drives scheduling (it's per-plan now) and `new Date()` is an absolute instant, so the server's zone is irrelevant to scheduling. **The `usableByHours` exception recorded here is RESOLVED** (corrected 2026-07-31): it now judges the instant on the venue's local clock via `isOpenAtInstant`, takes a `timeZone`, and both call sites pass the plan's zone. **The deployment TZ flag is RESOLVED** (2026-08-30): `DEPLOY.md` now states that `TZ=America/Toronto` is an optional compatibility/logging default, not a correctness requirement for multi-city scheduling.
- Transit legs get a +5 min delay margin; that buffer is separate from stop-duration buffers. A leg relabels as walk (no margin) when it's short (<400m), or when walking beats transit+margin AND the walk is ≤30 min (`MAX_WALK_LABEL_MIN`), or when walking is at least twice as fast as transit (broken-transit escape hatch, any length) — a 75-minute walk must never be presented over a similar transit ride.
- **Transit ride identity/palette metadata (2026-08-17, palette series Part 1):** every new computed leg has an app-owned `legId`; each source transit step gets one `rideId` and raw `sourceStepIndex` BEFORE facts/geometry filters diverge, and the same occurrence metadata plus `paletteSlot` reaches whichever `TransitSummary`/transit `PathSegment` sides survive. Never pair filtered arrays by position or infer identity from provider facts. Slots are unique `0..23` in home→inter-stop/provider order, with retained slots reserved first and explicit `null` overflow; legacy all-absent metadata remains valid and is never guessed, while partial new generations and relational conflicts are rejected (or the malformed decorative path is sanitized at the server boundary). Freshly recomputed legs get fresh IDs, untouched legs retain theirs. Walk steps have no ride slot. Part 1 itself changed no visuals or nonvisual semantics; Part 2 is the only UI consumer.
- **Transit ride palette display (2026-08-20, palette series Part 2):** a fixed browser-safe 24-colour table maps each valid slot directly to one app-owned occurrence colour across the exact ride's native primary line, same-colour changed halo, map bubble, compact badge and BOARD badge. Slotted text surfaces force white; provider colour/text colour remain factual metadata and control only legacy/all-absent and explicit-null-overflow fallback. Never wrap, hash, randomize, pair filtered arrays, or use reserved `#C8F000`. Changed is a wider/lighter same-colour emphasis, not a recolour. Embedded transit-leg walking stays neutral but is now materially stronger: `#4F6F7E`, `12px` repeated dots, primary `.88`/scale `2.0`, changed underlay `.24`/scale `3.6`, both transparent-stroke. Provider geometry, two-metre merge/0.5-metre minimum, ordinary whole-leg walks, cleanup, bounds, markers and all nonvisual behavior remain unchanged; exactly coincident static lines remain indistinguishable without future interaction and must never be offset.
- **Location (multi-city):** the CITY and STARTING ADDRESS are plain text inputs on the empty state — resolved by the purpose-built Geocoding API via `POST /api/geocode` and its own server-only `GOOGLE_GEOCODING_API_KEY` (corrected 2026-07-31 — this used to claim it reused the Places key with no separate Geocoding API; both halves are wrong). City results must be locality-typed; addresses are objectively checked against the resolved locality/region/country, and multiple valid matches enter `recovery.mode: "geocode"` rather than taking index zero. The chosen formatted city rides on `parsed.city` (app-injected, never LLM-inferred) so swap/reroute re-searches inherit it; the geocoded start is stored as `itinerary.home` and everything home-related reads `itinerary.home ?? HOME` (the Chestnut default exists ONLY for pre-multi-city itineraries and tests). Weather takes `?lat=&lng=`. The parse's `location` field is a neighbourhood WITHIN the city, never a city. Never silently fall back to Ossington/Toronto for a user-entered city. Real location services / geolocation remain deliberately unbuilt — plain queries only.
- **Persistence seam:** routes access the itinerary store ONLY via `loadItinerary`/`saveItinerary` (store.ts). KV env vars set → Upstash Redis REST is the source of truth (always read Redis, always write back after mutations — `withStatuses`' lock ratchet mutates even on GETs and refusals); unset → the in-memory Map (dev/e2e). Engines never touch the store. Serverless without KV fails loud. Deployment (env table, Maps-key referrer restriction, optional `TZ=America/Toronto` compatibility/logging default) lives in `DEPLOY.md`.

## Fail-loud surface (operational notes)
`app/lib/planGuards.ts` is THE surface for bad input — every degenerate/impossible/contradictory prompt must land there (or in `resolveStartTimeChecked`'s band messages) with a reason + suggested fix; an empty map or a borrowed error from another branch is the bug. Guard order in `runPipeline`: degenerate prompt (pre-model) → unparseable parse → contradiction → [clarify questions] → time band → all-pools-empty net → unmet constraint → PARTIAL-failure recovery (the interactive panel below). A hard refusal string is the right answer only when there's no real choice to offer; once there IS one (an inferred-time guess, a weather block, a partly-empty plan), it belongs in the recovery panel instead — see the next section. Constraints are enforced in `selectVenues`: no evidenced candidate → `id:null + unmet_constraint` (valid, no fallback), and a code-side hedge guard converts "worth confirming / may accommodate" picks into the same failure — never suggest a venue while telling the user to verify a constraint. `priceLevel` + `description` ride ON the stop (Selection → SelectionLike → ItineraryStop, set by swap's buildStop/finalize too); the strip must read the stop's own fields before any pools lookup, which goes stale after swaps.

## Shipped — interactive recovery panel (operational notes)
ONE component in `app/page.tsx` (`recovery` state, a discriminated union on `mode`), three triggers. Never build a parallel panel for a fourth case — add a mode.
- **`mode: "empty"`** — partial failure: some categories picked, ≥1 pool came back empty. `partialEmptyCategories` detects it (all-empty stays on `noVenuesReason`, never routes here). Each row shows `emptyCategoryReason` (the honest dominant reason from the objective drop log) + a widen offer (re-search city-wide via `categoriesOverride`, suppressed per-row by `noWiden`) + a free-text replace + "Plan without it" (shown only when some other stop actually resolved).
- **`mode: "geocode"`** — the purpose-built geocoder returned more than one valid typed city or in-city address. Show the formatted-address candidates and resume with exactly the chosen one; never take provider index zero. (Corrected 2026-07-31: this mode was missing here, and a `mode: "time-gate"` was documented that no longer exists — it was removed along with the plausibility gate on 2026-07-27. `page.tsx` has exactly three modes: `geocode`, `empty`, `weather-gate`.)
- **`mode: "weather-gate"`** — a category was emptied by the weather gate specifically, while others survived. "Still want it" re-searches that category with `weather: null`, which skips ONLY the weather gate via keep-on-missing — hours/rating/price/business status all still run, and no server change was needed. Resolved categories must be cleared from `weatherBlocks` (a planned stop is not "skipped"). Still-empty falls into `mode: "empty"`, never a third dead end. "Something else" scopes to the SLOT (replace rows with `noWiden`), not the whole-plan kind picker — other stops survived and discarding them would be wrong. The ALL-weather-blocked path keeps `weatherBlockedReason` untouched.
- Shared plumbing: `searchSlot` (one category search+select, with `dropLocation`/`ignoreWeather` switches) and `mergeSlot` — widen, replace, and both overrides go through the same fetch path. `orderByRequest` restores prompt order afterwards, because `selectVenues` appends empty categories LAST and recovery resolves them in that appended position.

## Shipped — swap engine (operational notes)
Per-stop swap (`app/api/itinerary/swap.ts`, `POST /api/itinerary/[id]/swap`): user taps an UPCOMING stop, types a complaint, the engine acts on intent — VENUE (replace, hold slot), TIME (move the slot), DURATION (change how long), or CONSTRAINT (re-search). Distinct from reroute (external disruption → downstream replan). `floorTime()` shared from `store.ts` by both engines.
- **Time / duration swaps**: `parseTimeExpr` (relative "an hour earlier" = -60, absolute "after 8" = 20:00, meridiem anywhere "6pm" = 18:00, bare "3:30" = 15:30 — assume PM only for meridiem-less times; a number owned by a duration unit, "make it 2 hours", is never a clock time) and `parseDurationExpr` (absolute "stay 2 hours" = 120, relative "stay longer" = +30) are the deterministic floors under the LLM interpret — arithmetic never depends on the model. Merge rules: a locally-parsed ABSOLUTE time always beats the model's; an EXACT local relative beats the model's; only a VAGUE local relative ("a bit earlier") accepts model refinement, and only same-sign ≤3h — garbage deltas must never drift a stop across the day. A phrase with BOTH halves ("start at 6pm for 2 hours") routes to time and applies the duration alongside via the shared `resolveNewTotal` bounds — neither half is ever dropped. A time-swap moves the slot, never resizes it, and a VENUE swap holds the whole slot, length included: the stop's customized `durationMinutes.total` is the source of truth everywhere a swap keeps the same category. It resets to the (new) category default only when the stop changes KIND — a category-changing research swap, or an engine-adapted replacement venue. The `[swap-apply]` log in `swapStop` prints intent + before/after start/total — check it first when a swap changes the wrong field. Both call the reusable **try → adapt → notify** ladder `resettleTail` (shift/reflow the tail, keep a downstream venue if still open at its new arrival, else re-search an equivalent, else fail loud). Plan-then-commit: a failed resettle leaves the itinerary untouched. Duration guards: floor at the category's realistic minimum, cap 6h. `buildStop` takes a `durationOverride`; `resettleTail`/`commitTail` carry each stop's `totalMinutes` so a custom duration survives a later reflow. Keep `resettleTail` generic — it's the shared spine of time + duration (and future) swaps.
- **Availability seam**: `SwapDeps.isUsableAt(place, when, category)` is the ONE "is this venue usable then" check (default = objective hours, keep-on-missing). A real availability/reservation API replaces that function body only.
- **UI**: the swap prompt is inline under the selected strip card (`ItineraryStrip` `SwapInline`), upcoming-only; reuses the reroute reflow (chartreuse "changed" keyed by venue id). The map's projection probe defers its `setState` to rAF (never call setState inside a Google `OverlayView.draw()`).

## UI invariants (don't regress)
- Acid green (`--live`) is reserved. The FULL chartreuse marker/border = the active "now" stop only. Swap-/reroute-changed elements get chartreuse *accents* (changed-ring marker and settling time pill), while the route keeps its own colour and gains a wider/lighter same-colour halo; an upcoming changed stop keeps its ink marker — chartreuse never means "changed" and "now" at the same visual weight. Never decoration.
- Swap vs reroute: swap is user-initiated + surgical (one upcoming stop, hold the slot); reroute is disruption-driven + replans the tail. Both share `floorTime()` and reuse the same pipeline cores — never fork a third replan path.
- Map uses inline `styles` JSON on a classic `Map` (no `mapId`) so paper styling works; markers/cards are `OverlayView` HTML, NOT AdvancedMarkerElement (which needs a Cloud map id).
- fitBounds keys off venue coordinates (`fitKey`), never status ticks — status changes must not yank the map view.
- Expanded cards clamp to the viewport (horizontal) and flip below the pin near the top edge.
